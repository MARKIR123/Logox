# LOGOX TS 开发流程

维护日期：2026-10-12。适用于需求讨论、功能迁移、修复、重构、UI 打磨和文档维护。

一次开发围绕一个能验收的目标展开：核对现状 → 记录方案 → 小步实现 → 验证与审查 → 改写当前文档 → 交付。用户决定目标、产品体验和重要技术取舍；开发者查证事实、处理授权范围内的实现细节。已确认的工作持续推进。

## 1. 开始前读什么

1. 读 [STATUS](STATUS.md)，确认当前优先工作与未验证项；用户本轮要求决定实际任务范围。
2. 读 [迁移总览](designs/2026-10-11-typescript-migration.md) 的阶段与架构边界，再从[专题索引](../README.md#专题设计与复盘)选择当前功能的设计，按 [模块地图](../modules/README.md) 找源码和测试。UI 任务同时读 [UI-SPEC](../UI-SPEC.md)。
3. 核对当前分支、工作区修改和真实调用入口。保留已有工作；文档与源码不一致时先写清差异。
4. 迁移旧能力时，对照原 LOGOX 的当前模块文档、源码和测试，记录准备继承的具体行为及 TS 验收方式。LEGACY/legacy 和明确标为 legacy 的材料不读取、不修改、不作为依据。

完成条件：能说明当前行为、目标行为、归属模块、修改范围和验证入口。依赖环境或源码能查到的事实由开发者查证。

## 2. 选择记录深度

| 任务 | 修改前 | 完成后 |
|---|---|---|
| 文案、链接、已确认方向下的配色与留白微调 | 核对范围与当前内容；在现有任务中写清目标 | 直接更新受影响说明，检查内容与链接或实际输出 |
| 恢复已确认行为的修复 | 记录触发步骤、实际/预期结果、依据、修改思路、验收条件 | 留下修复证据；典型诊断才另写复盘 |
| 新功能、产品行为变化、跨模块重构 | 在对应设计中说明行为、职责、接口、失败边界、实施步骤与验收；重要未决选择经用户确认 | 更新当前说明与设计状态，保留未完成工作 |
| 文档结构或开发流程调整 | 写清文件职责、读取入口和维护规则 | 检查单一维护位置、有效链接及与代码的一致性 |

记录深度由行为影响决定。单行快捷键若改变取消、提交或唤醒语义，也属于产品行为变化。用户已经明确指定的行为不重复请求确认。

设计按功能或独立设计问题归类：迁移总览维护整体目标、架构边界和阶段顺序；slash 交互、上下文压缩、提供商登录等专题各自维护方案、确认与验收。新主题新建对应文档，同一主题修订原文；日期表示建立时间，标题和目录说明主题。

每份专题按目标、职责、规则、失败边界和验收组织，确认结果直接写成有效规则；重要取舍保留理由与依据。一次变更通常只需要一份所属专题设计，不机械拆成规格、计划、任务三份。重要且需要独立查阅的取舍才写入 `development/decisions/`，典型排查才写入 `development/reviews/`，外部调查才写入 `development/research/`。这些目录有实际材料时再创建。

## 3. 收敛目标与验收

先解决范围与主要体验，再讨论依赖它们的细节。有影响的未决选择给出具体选项、优缺点、建议及以后改变的成本；答案能从实现中核对时先查证。

设计至少能回答：

- 用户或调用方要看到什么结果，哪些内容属于本次范围？
- 当前实现在哪，谁负责业务规则，哪些模块只负责接线或展示？
- 状态、数据和接口怎样变化；等待、取消、异常和恢复怎样收尾？
- 分几步接入真实调用链，每一步怎样验证？
- 哪些选择已确认，哪些待确认，哪些环境尚不可验证？

可直接在设计中使用以下简短结构，按任务删减：

```text
状态：待确认 / 已确认待实现 / 部分实现 / 已实现 / 被取代
问题与目标：
当前行为与证据：
确认方案、职责与接口：
实施清单与每步验证：
验收条件、实际结果与未验证项：
剩余工作与后继入口：
```

完成条件：方案能够指导实现，验收能够判断结果；实际需要用户判断的产品或架构选择已确认。设计写了目标，不代表能力已实现。

## 4. 小步实现与代码可读性

每一步完成一个可观察行为，并接入实际入口；行为成立时同步所属当前说明、设计状态和剩余事项。先验证该步，再推进下一步。实现发现重要假设不成立时修订设计；改变已确认体验或技术路线时再讨论，普通实现细节在既有授权内处理。

按职责维护代码：

- 活动状态、请求身份、许可裁决、任务取消和恢复规则放在运行时；TUI 负责显示与输入。演示场景的本地状态不成为业务协议的另一份权威。
- 目录表达实际职责。函数名说明动作，类型名说明数据用途；稳定的公开接口与内部细节分开。新增抽象要解决当前重复或边界问题。
- 共享协议在 `runtime/contracts.ts` 维护。外部输入先校验，再进入受信逻辑；保留项目严格类型检查设置。临时类型断言不能替代验证。
- 异步过程明确拥有者、等待点与收尾路径；谁创建任务，谁保证取消、失败或关闭后解除等待并留下正确终态。
- 同一函数混合业务判断、状态更新与渲染，或同一文件出现独立职责时，按当前改动范围拆开。按完整职责拆分，不以行数拆出无意义工具文件。
- 注释说明代码本身看不出的原因、约束和边界。设计比较与排查过程留在文档；重复代码动作的注释可以删去。
- 测试覆盖调用方可见的结果和相关失败边界。修复在能复现真实问题的层次建立回归；可逆低影响改动不为了形式新增测试。

完成条件：该步已接入，边界清楚，相关验证通过；未完成步骤保持未完成状态。

## 5. 验证与审查

按 [TESTING](TESTING.md) 选择定向检查和必要回归。先看原始目标是否满足，再看相关失败边界与既有行为。新修改、失败或未解决的影响范围才触发扩大或重复检查。

交付前分别审查：

1. **需求一致性**：实际行为是否符合已确认设计，是否遗漏等待、取消、恢复或窗口同步？
2. **维护一致性**：职责与依赖是否清楚，共享规则是否只有一个维护位置，代码与当前文档是否一致？

检查按任务影响执行，不强制为每次小改动创建独立审查文件或启用多代理。发现问题先修复，再验证受影响部分。

完成条件：每项验收都有实际结果。模拟 TTY、真实 Windows Terminal、真实模型和外部服务分别记录；未执行的检查保持未验证。

## 6. 文档收尾与接手

| 信息 | 唯一维护位置 |
|---|---|
| 最短运行方式与项目入口 | 根 README |
| 如何找到相关文档 | docs/README |
| 当前职责、机制、接口与失败边界 | docs/modules/README；内容有独立阅读需要时再拆模块文档 |
| 当前界面布局、主题、焦点和交互约束 | UI-SPEC |
| 开发步骤与代码维护约定 | 本文 |
| 验证方法与环境要求 | TESTING |
| 当前未完成/未验证事项与下一步 | STATUS |
| 整体迁移目标、架构边界和阶段顺序 | 迁移总览 |
| 某项功能的方案、确认和实施结果 | 所属专题设计 |
| 典型问题的触发、定位、修复和回归证据 | 对应复盘 |
| 已有界面术语 | 根 GLOSSARY |
| Agent 必须常驻的约束与按需读取入口 | 根 AGENTS |

当前说明直接改写有效规则，移除已经失效的说法和重复段落。专题设计按概念维护已确认方案；重要取舍保留理由，既有验收证据标明日期，状态与后继入口随实现更新。测试数量、耗时和截图属于验收证据，不进入当前使用规范。

STATUS 只保留待完成事项：写清影响、下一步和验收方式；已完成项移出，必要历史留在设计或 Git。正式说明不能依赖忽略目录里的截图、会话原文或临时脚本才能读懂。

完整签名、依赖版本和脚本列表以源码、锁文件、配置为准，文档引用路径和关键符号。新增文档先说明独立用途，并从现有入口链接；正文能清楚承载时原地修订。

### 随开发推进的整理时机

- 开始任务时，确定所属专题和受影响的当前说明；发现过时内容先核对真实行为。
- 每完成一个可观察功能，或确认改变既有行为时，改写对应说明、设计状态与 STATUS。新主题分开成文并接入导航；同一主题调整相关段落。
- 交付前，清理本次影响范围内的失效说法、重复规则、已完成待办和旧章节引用；核对读取入口与实际源码。

文档完成的标准是读者能够据此操作、找到职责和失败边界、区分已实现与未验证，并从 STATUS 接手剩余工作。内容审查对照源码和验证证据；结构检查运行 npm run check:docs，已接入 npm run check 和 npm test。

## 7. 交付条件

- 原始目标与相关边界有结果；失败、未验证和已有问题明确记录。
- 当前说明已同步代码和验证证据，旧规则与重复段落已清理，文档检查通过。
- 设计状态已更新，STATUS 中剩余事项可以直接接手。
- 改动范围清楚，已有修改、原 LOGOX 与私人运行资料得到保留。
- 提交、推送、合并和发布按已有用户授权执行；当前未提交也明确报告。

交付说明先写完成内容与验证，再写重要原因和下一步。可逆文档维护用内容、链接与保持性检查即可。
