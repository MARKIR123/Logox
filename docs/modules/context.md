# 上下文管理

模型每次请求能带的内容有上限，但完整的过程记录不应该因为压缩而丢失。这个模块把“原始账本”和“发给模型的视图”分开：账本只追加、不改写；每次请求时再从账本里挑出当前需要、预算装得下的部分。

## 核心概念

- **Journal（账本）**：每个会话、每个角色的原始 JSONL 记录，只追加。恢复和回读都以它为准，见 `src/store/journal.ts`。
- **轮（round）**：从一个活动的最初输入，到它完成、失败或取消。同一活动中途注入的协作消息不另算一轮。
- **有效视图**：本次请求真正带上的历史，由账本经过归档、折叠、收缩得到，账本本身不变。
- **`_FinishRound`**：每个正常结束的轮会调用的隐藏工具，用来提交这一轮的内部记忆。它不显示成工具卡片，也不算用户授权。
- **高水位 / 低水位**：高水位是触发整理的上限，低水位是整理后要降到的目标。整理会重置提示词缓存，所以触发后一次降到低水位以下，而不是零碎地压。
- **ContextManager**：每次请求前组装有效视图的组件。

## 一次请求前发生什么

1. 根据角色、本任务实际使用的模型、轮次和工具身份，从账本组装有效视图。真人输入、派工、角色报告和协作消息保留各自的来源，角色的数据不会被当作人工授权。
2. 估算 token 是否超过高水位。没超过就直接发送。Logox 统领全局，平时保留完整历史；Techne、Kalon、Aletheia 按任务工作，每开始一个新任务就把之前已结束的轮折叠起来。
3. 超过时依次整理，每一步后重新估算：
   1. 较大的旧工具参数和结果归档到磁盘，视图里只留可回读的指针。
   2. 已结束的轮折叠成单行索引：`序号 | 标题 | 状态; 验证 | 结果 | 遗留 | 账本行号`，内容来自这一轮 `_FinishRound` 的记录。仍超过低水位时折叠全部已结束的轮。
   3. 仍超过低水位时，最近 20 条索引（`keep_index_lines`）保留原样，更早的历史由模型合并成一份工作概览，上限约 4000 token。
   4. 当前任务自身仍超过高水位时，由模型写一份进度摘要，替换这个任务已完成的过程，原始输入保留。

   第 3、4 步在对话末尾追加一条整理说明，让本任务的模型直接总结，这样请求能复用已缓存的对话前缀；汇总模型与任务模型不同或总结失败时，退回到分段汇总和程序提取。
4. 仍无法容纳，就停止这次业务请求并说明原因；原文和已完成的操作不受影响。

整理在完整的工具批次边界进行，不会把一次工具调用和它的结果拆开。`/compact` 手动触发同一流程。

**任务结束时的整理**：actor 只在一个真实任务结束时（Director 派发的任务，或人类直接交给该 actor 的任务）才会顺带整理一次。协作提问、同伴唤醒、回复和中途插话产生的活动不触发，新活动开始也不会因为存在已关闭轮次而强制整理；这些轮次留到下一个真实任务结束或越过高水位再处理。任务结束时还有两道门槛：

- 下限：当前上下文低于高水位的 50%（`task_end_floor_ratio`）时直接跳过，保住提示词缓存。
- 收益：整理结果必须不超过原估算的 75%（`compact_accept_ratio`），否则丢弃候选、保持当前视图，也不发“已整理”提示。

越过高水位触发的整理不受这两道门槛影响，规则不变。

整理之后，整理点之前产生的思考内容不再发送，工具调用和文字保留。Anthropic 新模型的思考块签名绑定了它之前的全部内容，整理后这些内容已经变了，继续发送会被拒绝；其他服务也不需要这些旧思考。

## 保留多少原文

默认值来自各角色 `config.yaml` 的 `context` 配置：

| 角色 | 保留的近期完整轮 | 保留原文的近期工具次数 |
|---|---|---|
| Logox | 2 | 2 |
| Aletheia、Techne | 0 | 2 |
| Kalon | 0 | 0 |

当前正在进行的轮和还没配对的工具批次另有保护，不会被折叠。

## 水位与预算

高水位 = `min(max(窗口 - 输出预留, 窗口 × high_watermark_ratio), max_budget_tokens)`，`high_watermark_ratio` 默认 0.8，保证小窗口模型也有可用空间。例如窗口 1,000,000、预留默认 32,768，且没设预算上限时，高水位是 967,232；窗口 32,768 时是 26,214。低水位只是整理的目标，不会提前触发整理。参数见[配置示例](../../config.example.toml)。

模型窗口按“配置覆盖 → 服务目录 → 内置能力资料 → 模型名推断”的顺序取得。未知的模型需要自己配置 `context_window`；本地服务要填实际分配的窗口，不要填型号的理论上限。内置 `gpt-6.1-sol` 的窗口是 1,000,000，显式配置仍可覆盖。

token 估算（`TokenMeter`）优先用上一次响应的真实 usage 作为锚点，再估算之后新增的消息。换模型或换工具集会让旧锚点失效。图片 base64 不计入文本，每张图暂估 1,200 token，这是预算估计，不是供应商的精确计费。

## 系统提示与工具披露

系统提示固定六个主题，按变化的可能性从上往下排：`Persona`、`Execution Rules`、`Team Collaboration` 是固定文本；之后是 `Project Guidelines`、`Tools & Skills`、`Current Environment`。两部分之间有一个缓存边界，固定部分在换项目、开新会话时仍能命中缓存。模型、权限、恢复和能力的变化不改动系统提示，而是作为程序来源的 `context` 记录追加到历史末尾，不冒充用户任务。

工具定义按需披露：支持的服务（如原生 Anthropic、OpenAI Responses）只先发送工具名，模型需要时再展开完整定义；不支持的兼容端点直接发送完整工具集，不保证省 token。整理历史时，会保留证明“这些工具已被发现”所需的最少记录，旧记录不会让已移除的工具恢复可用。这套估算是本地保守估算，不调用额外的计数接口。

## 用量与费用

任务、汇总和审批的用量都记入同一个 `UsageLedger`。`/usage` 按静态价格表估算费用，缺少 usage 或价格时不会伪造精确账单；回退对话不会删除已发生的消费。

## 边界与限制

- 压缩从不改写或删除账本的原始行；摘要里的位置引用的是账本中的真实行号。
- 恢复只恢复记录和有效视图，不重放历史工具。`/rewind` 之后，未来的内容不会因为缓存重新进入请求。
- 摘要来源改变或归档缺失时，回落到原文；原始账本损坏则直接报错。
- 失败、取消或元数据缺失时，使用保守兜底，保留实际交付和真实终态，不编造“已验证”。
- 压缩调用模型时仍可能失败、取消或产生费用，它不等于无限上下文。
- 大块工具输出存放在所属账本的 `.tools` 目录，按指针回读时仍要通过权限检查。

细节和不变量见[上下文路标](../../src/context/AGENTS.md)。
