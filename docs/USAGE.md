# 使用 Logox

本文是用户手册：从首次连接模型、配置、提交任务，到会话、权限、扩展和全部命令。安装步骤见[项目 README](../README.md)，快捷键与鼠标操作见[终端操作](UI-SPEC.md)。正式对话需要交互式终端；目前没有 headless、JSON 输出或 `--prompt` 模式。

## 首次连接模型

首次安装时没有预先选好的模型，也不会自动安装或下载本地模型。第一次启动且尚未选择模型时，会自动打开设置向导；设置向导开头有一个可选步骤“What should Logox call you?”，输入称呼后回车；直接回车或按 `Esc` 跳过，向导继续。已经完成过首次引导的用户升级后不会再被询问，可随时用 `/name` 设置。之后可随时用 `/setup` 重新打开。也可以直接输入：

```text
/login
/model
```

`/login` 打开提供商向导，`/login deepseek` 直接进入指定提供商（`/login openai` 是 API key 流程，`/login openai-auth` 是账号流程；名字不在列表里会报错）：没设置过就是它的添加流程，已设置就是它的编辑菜单。向导没有“新增/编辑”之分，根是两种登录方式（各两行）：`API key`（Sign in with a URL and an API key）和 `Account sign-in`（Authorize in the browser with a provider account）。

**API key 列表**：

- **顺序**：全部列出的内置模板（按模板顺序），然后是你自己的提供商（自定义记录、配置文件里声明的提供商，也包括曾经作为模板的本地代理，例如已有记录的 `antigravity`），再然后是没有对应记录的孤立凭据，最后一项固定是 `Custom endpoint`。
- **每一项两行**：第一行左边是名称，右边靠右对齐一个状态徽标，由“来源 · 状态”组成：来源是 `built-in` 或 `custom`；状态是 `✓ signed in`（已保存 API key）、`✓ env key`（只有模板的环境变量提供密钥）、`✓ local`（有记录的无需密钥的本地端点），尚未设置则只有来源。账号登录的提供商（`openai-auth`）不在这张列表里。如果 `openai-auth` 已账号登录、而 `openai` 自己没有 key，`openai` 的徽标是 `built-in · account signed in`，其中 `account signed in` 用主题的提示色（`link`，既不是成功色也不是警告色）：它只提醒“OpenAI 已经能通过账号使用”，不是这一项自己的状态；这个提示来自模板的 `accountSibling` 声明，不是写死的 OpenAI 判断。`openai` 有了自己的 key 后徽标恢复为 `built-in · ✓ signed in`。`✓` 部分用主题的成功色，其余为暗色；孤立凭据显示警告色的 `credential only`。第二行是暗色说明：模板是一句简短描述，自定义提供商是 base URL，`Custom endpoint` 是 “Any OpenAI- or Anthropic-compatible URL with an API key”。终端很窄时先截断名称，再去掉来源，徽标始终可见。鼠标：单击选择，悬停高亮，滚轮滚动。
- **选没设置过的模板**：直接进入添加流程：地址（模板的官方地址已预填，直接回车即保留，也可以改成自己的地址）、key（内置模板都需要 key；无需密钥的端点走 `Custom endpoint`）、模型、确认保存。`openai` 与 `openai-auth` 是两个互相独立的提供商，保存 `openai` 的 key 不会影响账号登录，因此没有任何“替换”确认。
- **选已设置的提供商（内置或自定义）**：进入它的编辑菜单：`API key`、`Base URL`、`Wire protocol`、`Model list`，以及 `Delete provider`（没有可删内容时不显示，例如只靠环境变量的模板）。每个有记录的提供商都可改地址和协议。删除需再次确认。如果有人在用这家提供商的模型（当前会话、某个角色的默认模型、Automa 的专用模型），确认框会列出 `In use by: session, techne, ...`；确认删除后这些角色或 Automa 的绑定会被清除，不会被悄悄改成别的模型，并发出一条提示列出需要重新指定的角色（用 `/model <角色>`）。没有绑定的角色沿用会话模型；如果会话模型本身在被删的提供商上，会话回到“未选择模型”，需要用 `/model` 重新选。
- **选孤立凭据**：只能删除。
- **选 `Custom endpoint`**：路由名、key（可留空）、地址或端口与协议（Chat Completions、Responses 或 Anthropic Messages）、模型、确认保存。路由名不能与列表里已有的重复。本地代理（如 antigravity）也从这里添加。

**Account sign-in 列表**：列出账号专用的模板（由模板的 `account` 属性决定，目前只有 `openai-auth`，说明为 “ChatGPT account (subscription)”），同样两行并带徽标：账号登录的显示 `built-in · ✓ account`，其余只显示来源。选尚未账号登录的会直接启动浏览器授权，没有确认框。选已账号登录的会进入它的菜单：`Sign in again`（重新授权）、`Model list`、`Delete provider`（同样的使用情况确认），没有 API key、地址或协议项。`✓ account` 只出现在这张列表里，其余状态只出现在 API key 列表里。没有任何模板支持账号登录时提示 “not supported”。

**模板与提供商**：模板是内置的快捷方式，只包含名称、固定的官方地址和协议（`openai`、`openai-auth`、`anthropic`、`deepseek`），本身不是提供商。本地代理 `antigravity` 不再是模板，而是一个用户自己的自定义端点：程序仍认识它的默认地址和 Claude 路由，已有记录照常工作，在列表里显示为 `custom · ✓ local`。提供商是你设置过的东西，每个提供商在 `~/.logox/custom-providers.json` 里有一条记录；模板只负责预填：新增时地址默认取模板的官方地址，之后记录自己拥有地址、协议和 `api`，你可以随时在编辑里修改，启动时不会再用模板覆盖。基于模板的记录带 `catalog: true`，模板只补记录里没存的东西：密钥环境变量，以及仅当记录的地址仍是模板官方地址时才生效的 `model_kinds` 路由。账号登录（OAuth）是提供商的一种凭据类型：账号专用模板由 `account` 属性标出，目前只有 `openai-auth`，它没有 API key 流程也没有密钥环境变量；用账号还是 key 由凭据类型决定，不看提供商名。旧的 `openai-compatible` 模板已移除（它与 `openai` 地址和环境变量完全相同）：旧配置或已保存选择里仍写着这个名字（且没有自己的 `base_url`）时，会静默按 `openai` 解析，不会出现在任何列表里；全新安装的默认提供商现在是 `openai`。

列表中的“提供商”依次包括：已保存的记录、配置文件里声明的 `[providers.<name>]`、已设置对应密钥环境变量的模板（零配置可用），以及当前选中的提供商。没有设置过的模板不会出现在提供商列表、`/model` 和 `--list-providers` 的主列表里，只出现在 `/login` 列表里（以及 `--list-providers` 末尾的 Templates 小节）。保存 key 或完成账号登录时会自动创建记录；启动时，`auth.json` 中名称是模板、却没有记录的凭据会补写一条记录。名称既不是模板、记录也不是配置提供商的凭据不会被自动改动或删除，在列表里显示为 `credential only`（说明 Saved credential without an endpoint），只能删除。删除提供商会同时删除记录和凭据。

保存确认前取消不会写入任何内容。密钥只留在本地表单和认证存储中，不进入工具问答、会话账本或模型上下文。向导不会扫描其他工具的凭据文件。登录期间聊天草稿仍可编辑，但暂时不能提交聊天或其他命令。表单内的按键见[终端操作](UI-SPEC.md)。

**两个 OpenAI 提供商**：`openai` 只用 API key（按量付费），`openai-auth` 只用 ChatGPT 账号登录（订阅）。两者各有自己的记录、凭据、模型列表和模型选择器条目，可以同时设置，角色也可以分别绑定到其中一个，互不替换。

**一次性迁移**：以前账号登录保存在 `openai` 名下。升级后第一次启动时，如果 `auth.json` 里 `openai` 的凭据是账号登录（OAuth），Logox 会把它移到 `openai-auth`：先写入新名字并读回确认，再删除旧的；任何一步失败都保持原样（凭据不会同时消失）。如果 `openai-auth` 已有凭据则不覆盖，两边都保留，迁移跳过。同时改写这些把 `openai` 当作账号提供商的引用：`openai` 的提供商记录（模型与默认模型带过去）、`~/.logox/model-preferences.json` 与当前项目 `.logox/state/model-preferences.json` 里保存的选择、`~/.logox/actor-models.json` 与 `tool-models.json`（角色与 Automa 绑定）、`~/.logox/models-store.json`、`~/.logox/actors/` 与当前项目 `.logox/actors/` 中角色文件的 `defaultModel`。迁移后发一条提示 `OpenAI account sign-in is now the provider openai-auth; your saved model choices were updated.`。`openai` 的凭据是 API key 时不做任何事，重复启动也不会重复执行。会话账本、旧会话的任务模型记录、其他项目的状态和 `config.toml` 里写的 `openai` 不会改：它们仍指向 `openai`，使用时按 `openai` 的正常路径报 “not logged in”（恢复旧会话不会崩溃，也不会悄悄改用账号），用 `/login` 或 `/model` 重新选择即可。

认证保存在 `~/.logox/auth.json`，与项目聊天账本分开。读取优先级是：Logox 保存的认证，其次是指定的密钥环境变量，最后是显式配置的只读认证文件。`auth_file` 支持兼容的 API key 记录和完整的环境变量引用，不支持执行命令取密钥，也不同于 Logox 自己的 OAuth 登录。

`/model` 查询已认证或已配置服务的模型目录，并按提供商分标签页展示；每个模型行显示自己的上下文窗口和思考档位，档位滑条只作用于当前选中的模型。某一家查询失败不影响其他服务。`/models` 只列出当前提供商的模型。也可以直接指定：

```text
/model provider/model-id
```

把 `provider/model-id` 换成目录中的实际名称。只写模型简称时，可能按缓存匹配到别的提供商；要明确服务，请使用完整形式。

### 模型档位与视觉标记

每个模型有两个标记，只用来帮你筛选和挑选模型：**档位** `T1`–`T4`（`light`、`standard`、`strong`、`frontier`，参照 Haiku、Sonnet、Opus、Fable）和 **视觉** `◉`（能看图）。**Logox 从不按任务难度猜测、切换模型**：谁用哪个模型由你指定，或由确定的规则决定。Automa 工人按作业有没有 `writes` 授权分到读取模型或代码模型，未绑定时按档位和价格自动选（见下）；另一个自动切换是看图：带 `vision: true` 的 Automa 作业遇到不能看图的模型时，改用视觉后备模型。

- **默认值**：已知系列按名字对应（`haiku` → T1，`sonnet` → T2，`opus` → T3，`fable`、`mythos` → T4，不分大小写，匹配模型 id 或目录里的名称）。其他模型在同一服务商内按输入价格排成四分位（最便宜 T1，最贵 T4）；服务商里有价格的模型少于四个时按绝对价格：低于 $0.8 为 T1，低于 $2.5 为 T2，低于 $8 为 T3，其余 T4。没有价格也不属于已知系列的模型是 T2。模型表的输入类型含 `image` 的算能看图；模型表里查不到的模型当作能看图。
- **显示**：`/model`（会话、`/model <角色>`、`/model automa`、`/model anamnesis`）的每个模型行末尾显示 `T2 ◉`，`/models`、`/providers` 页和设置里的 Models & pricing 也带同样的标记。灰色是默认值，正常颜色是你改过的；你把视觉标记关掉的模型显示 `○`。
- **筛选**：列表顶部一行 `All · T1 · T2 · T3 · T4 · ◉ Vision`，单击即选；键盘用 `[` / `]` 前后切换（`Tab` 已用于切换提供商）。切换筛选时，仍然可见的当前选中项保持不变。
- **修改**：选中模型行后按 `1`–`4` 设定档位，`v` 切换视觉，`0` 清除你的改动、回到默认值；单击行尾的 `T…` 在 T1–T4 间循环，单击视觉位切换视觉。修改立即保存到 `~/.logox/model-tiers.json`（`{"version": 1, "models": {"provider/model": {"tier": 3, "vision": false}}}`）并刷新，你的值优先于默认值；文件损坏时只读默认值，且不会被覆盖。搜索框里已有文字时，这些单键属于输入；此时用 `Alt+1`–`Alt+4`、`Alt+v`、`Alt+0`。
- **图片兜底**：请求要把图片交给一个视觉标记为否的模型时，图片换成一行 `[Image omitted: <model> cannot see images.]` 和下一步提示（工人：让派遣者带 `vision: true` 重派；角色：请用户为该角色换一个能看图的模型）。工人的回执 `Not verified` 里会多一行 `Images were omitted: <model> cannot see images.`。

两个检查手段的区别：

- `/check-provider` 会发送一次真实请求，可能计费。
- `--check-config` 只显示配置和认证是否存在，不证明远端可用。

遇到环境问题（Node 版本、终端能力、Playwright 浏览器、角色档案、凭据）时，运行 `npm run doctor` 或 `--doctor`，在会话内也可输入 `/doctor`。`/doctor` 已登记在命令列表中，`/help` 和候选菜单里都能看到；面板内的结果按主题颜色着色，不再输出原始 ANSI。

## 配置

通常用交互命令即可：

- `/theme`：主题页，带实时预览和可读性检查；详见下文“主题页”。
- `/settings`：按分组列出外观、启动页和对话偏好，并可进入状态栏、权限、模型与价格、快捷键页面（`/animations` 是旧别名）。详见下文“设置页”。
- `/config`：只读的生效配置，包括当前模型、思考档位、Base URL 和执行限制。
- `/status`：运行状态；用量页签只显示会话总计，并提示 `Details: /usage`。
- `/usage`（别名 `/cost`）：本会话的费用与用量明细，见下文“用量页”。

需要固定参数时，参考 [config.example.toml](../config.example.toml)，放到用户级 `~/.logox/config.toml` 或项目级 `.logox/config.toml`。

### 加载顺序

从低到高依次为：

1. 默认值
2. 用户配置：`~/.logox/config.toml`
3. 项目祖先目录配置，从远到近
4. 当前项目 `.logox/config.toml`
5. 已保存的模型偏好
6. `LOGOX__` 环境变量
7. CLI 参数

高层覆盖低层，同一物理文件只加载一次。旧目录 `~/.logox-ts` 已不再读取，`logox --doctor` 会提示迁移。模型偏好以项目数据目录（见“数据位置与构建”）为主，其次是 `~/.logox`。切换提供商不会继承上一家的地址、模型或认证设置。

环境变量用双下划线分层，例如 `LOGOX__PROVIDER__MODEL`、`LOGOX__KERNEL__MAX_ITERATIONS`。启动时会尝试读取当前目录的 `.env`。配置文件不接受直接保存 `api_key`，请用 `/login` 或 `api_key_env`。

### 内置服务与自定义接口

| 名称 | 协议 | 默认地址 | 密钥环境变量 |
|---|---|---|---|
| `openai` | OpenAI 兼容（按量付费，只用 API key） | `https://api.openai.com/v1` | `OPENAI_API_KEY` |
| `openai-auth` | ChatGPT 账号登录（订阅，只用浏览器授权，始终走流式 Responses） | `https://api.openai.com/v1` | 无 |
| `deepseek` | OpenAI 兼容 | `https://api.deepseek.com` | `DEEPSEEK_API_KEY` |
| `anthropic` | Anthropic 原生 | `https://api.anthropic.com/v1` | `ANTHROPIC_API_KEY` |
| `antigravity`（不在模板列表，经 `Custom endpoint` 添加；已知端点） | 本地代理：默认 OpenAI 兼容，`claude-*` 模型走 Anthropic 原生 `/v1/messages` | `http://127.0.0.1:8045/v1` | 通常无需配置 |

同一个提供商可以按模型切换协议：`model_kinds` 把模型名模式（`*` 匹配任意字符，不区分大小写，先匹配先用）映射到 `openai_compat` 或 `anthropic`，未命中的模型保持提供商自身的 `kind`。`antigravity` 预置了 `{"claude-*" = "anthropic"}`：同一地址和端口，Claude 模型发往 `/v1/messages`（思考、缓存断点、用量都按 Anthropic 协议），Gemini 等仍走 `/chat/completions`。预置只对预置地址生效；自定义时写在 `[providers.<name>]` 或 `[provider]` 下，写 `{}` 可关闭。`[provider] kind` 显式设置时整体固定为该协议。

```toml
[providers.work]
kind = "openai_compat"
base_url = "http://127.0.0.1:8045/v1"
model_kinds = { "claude-*" = "anthropic" }
```

使用 `reasoning-effort` 思考协议（如 antigravity 的 Gemini）的 OpenAI 兼容请求不再把历史思考作为 `reasoning_content` 回传，避免代理把正文误标为思考后被当作示范。DeepSeek 等需要回传的提供商不受影响。

较弱的开源模型或 OpenAI 兼容网关偶尔会把工具调用写进回复文本（JSON、`<tool_call>` 标签或 `<invoke>` XML），而不是结构化的工具调用字段。Logox 会在回复里认出对本次请求已提供工具的调用并真正执行：参数仍走工具自己的校验和权限，回复里的调用文本被移除（前后的文字保留），并提醒模型下次使用结构化的工具调用格式。被截断的 JSON 只有在补全括号即可成立、且必填字段齐全时才会恢复；未知工具或无法解析的文本保持原样。模型把运行时插入的文本（提醒、读取墓碑、`<persisted-output>` 等）原样复述成回复时，这段文字不会显示或交付，Logox 会提醒模型继续任务，连续三次后以明确错误结束这一步。

Ollama、LM Studio 等本地服务需要显式定义。先启动本地服务，再在项目配置中添加：

```toml
[providers.local]
kind = "openai_compat"
base_url = "http://127.0.0.1:11434/v1"
default_model = "your-model-id"

[provider]
name = "local"
```

把 `your-model-id` 换成实际可用的模型。Logox 不会启动该服务，也不会验证本地模型实际分配的上下文是否与声明一致。

### 窗口、输出与超时

- `provider.max_tokens` 是请求输出上限，还会按模型能力和剩余窗口裁剪。
- `provider.timeout` 默认 600 秒，表示连续没有有效模型进展的期限，不是整个任务的最长时间。正文、思考和工具参数都会刷新期限，空心跳不会。
- `kernel.max_iterations = 0`（默认）不限制模型往返次数；设为正数时，达到额度会询问是否继续。取消随时可用。
- 模型窗口来自配置、目录或能力推断，未知能力需显式配置。以服务实际窗口为准。
- 图片：每张进入历史的图片都有磁盘文件（`Read` 用源文件路径，浏览器截图等写入调用者草稿区的 `images/`），路径写在工具结果文本里，之后不再改变。请求里图片原样内联，没有滑动窗口。整理上下文时，被归档部分的图片变成 `[image: 路径]` 文字，只有保留的近期部分仍内联。
- `max_images`（可写在 `[provider]` 或 `[models."p/m"]`，可选）是单次请求的图片上限；Anthropic 协议默认 100（官方上限），其他协议默认不设，只在服务拒绝“图片过多”时处理。超限时一次性把最旧的图片换成 `[image: 路径]`，直到约剩上限的一半，并保存这个决定，之后的请求保持字节一致；服务拒绝时同样降一半后重试一次。旧配置没有这个键，行为不变。
- 工具结果超过 32768 字符落盘到 `tool-results/` 并只留预览；同一轮并行工具结果合计超过 200000 字符时，按从大到小继续落盘，直到总量不超过上限。两项都在结果产生时决定一次，不会事后改写。
- `/effort`（别名 `/thinking`、`/think`）选择当前模型支持的思考档位；不支持的档位不会因此可用。
- `/usage` 的费用按每百万 token 的静态价格估算（先看 `[models."p/m".prices]`，再查[内置模型表](modules/model-table.md)；自建网关用 `[catalogs.<name>]` 指定对应目录），不是提供商账单；服务未返回的 usage 不会被补造。有模型查不到价格时，费用只算有价格的部分并标为 partial，用量页会多出几行：列出无价格的模型及其调用次数（最多几个，其余写 `+N more`），并给出可直接粘贴的 `[models."<provider>/<model>"]` 配置（`prices = {input = ..., output = ...}`，单位为每百万 token，另有可选的 `cache_read`、`cache_write`、`currency`）；自建网关上若内置表里恰好只有一个同系列模型，还会附上 `[catalogs.<provider>.aliases]` 的写法（别名按模型 id 逐个写，仅在两者计价相同时使用）。Models & pricing 页里没有价格的模型整行用暗色显示并写着 `no price`。`scripts/score-session.mjs` 的缺失项也会列出无价格的模型 id。

### 网络

生成请求与模型目录共用网络层。可在启动终端前设置 `HTTP_PROXY`、`HTTPS_PROXY`、`NO_PROXY` 等代理变量；未设置环境代理时，还可能读取 settings 里的 `httpProxy`。

所有连接都开启 TCP keep-alive（静默 10 秒后开始探测，经代理时同样适用），避免 NAT 或代理把“空闲但仍然存活”的连接当作死连接切断；这不改变任何超时设置。重试沿用流式请求，不会降级成静默的非流式请求；只有服务明确返回“不支持流式”（例如 HTTP 400 “streaming is not supported”）时，才用同一请求去掉 `stream` 重发一次。

部分提供商不输出思维链，长时间思考期间流上没有任何增量；无进展期限仍是 `provider.timeout`，没有新增超时。Gemini 的 OpenAI 兼容端点可以流式返回思考摘要：在 `[provider]`、`[providers.<name>]` 或 `[models."provider/model"]` 下设置 `stream_thoughts = true`（范围越具体优先级越高，默认关闭，不设置时不会发送任何额外字段），请求体会带上 `google.thinking_config.include_thoughts = true`，返回内容里 `<thought>...</thought>` 之间的文字显示为思考，并像其他思考增量一样刷新无进展期限。只在确认端点接受该字段后开启：严格校验字段的网关可能返回 400。思考档位为 `off` 时不发送。

连接中断和无进展超时会有限次重试。模型只返回思考或空回复时，运行时先用一条固定提醒（“Your previous reply was empty. Continue the task: call a tool or give your answer.”）自动重试一次，之后才进入原有的恢复与失败流程。已完成的工具不会因恢复而重放，写到一半的工具参数不会执行。重试耗尽后历史和失败状态都会保留，由你处理原因或明确继续；认证、额度、协议类错误不会一律自动换模型。

### 工具发现

模型默认直接可用 `Read`、`Write`、`Edit`、`Glob`、`Grep`、`Shell`、`ShellJob`、`AskUserQuestion`、`WebFetch`，其余工具在需要时通过 `LoadTools` 加载。加载只是让模型看到工具契约，不会执行工具，也不授予权限。

`Write` 拒绝整体改写已有的大文件（超过 20 KB 或 400 行）：被拒绝的内容会先保存到调用者自己的 scratchpad（`rejected-writes/` 目录），拒绝信息里给出保存路径，并建议改用 `Edit`；确实需要整体替换时再传 `overwrite: true`。

### 后台命令

服务器、监视器这类不会退出的命令用 `Shell` 的 `run_in_background: true` 启动：命令脱离本次调用，立即返回任务 id（如 `job-1`）、pid 和启动阶段的初始输出，不会占满前台超时。之后用 `ShellJob({id})` 读取自上次读取以来的新输出（超过 32 KB 的旧输出会丢弃），`ShellJob({id, stop: true})` 结束整个进程树。后台任务随启动它的任务一起结束（完成、失败或被取消），应用退出时全部结束；因此要在需要它的那个任务里启动。Automa 工作者不能使用后台模式。

`tool_discovery` 可取 `auto`、`none`、`anthropic`、`openai-responses`，在 `[provider]`、`[providers.<name>]` 或 `[models."provider/model"]` 下设置，范围越具体优先级越高，默认 `auto`。`auto` 只对明确登记的官方端点和模型启用原生协议；代理、别名和兼容服务一律使用普通完整工具集。显式选择原生协议表示你确认服务兼容，Logox 不会探测远端。

`prompt_cache_key` 为布尔值，设置位置与优先级同 `tool_discovery`。官方 `https://api.openai.com/v1` 默认开启：每个会话与角色发送固定的不透明键（`prompt_cache_key`），帮助 OpenAI 把同一前缀的请求路由到同一缓存；其他兼容网关默认不发送该字段，确认服务接受后可设为 `true`。键只影响路由，不保证命中。

### 提示缓存保留与保活

`cache_retention` 取 `short` 或 `long`，在 `[provider]`、`[providers.<name>]` 或 `[models."provider/model"]` 下设置，范围越具体优先级越高，默认不设置。它决定 Anthropic 提示缓存的生命周期：`long` 在每个断点写入 `cache_control: {type: "ephemeral", ttl: "1h"}`（一次请求只用一种生命周期，写入价 2 倍），`short` 保持默认 5 分钟（写入价 1.25 倍）。未设置时按角色取默认值：Director（logox）为 `long`，因为它要长时间等待派出的任务；其他角色为 `short`，因为它们在紧凑的工具循环里，更长的生命周期只增加写入成本。单个角色可在自己的 `config.yaml` 里写 `cache_retention: long`（或 `short`），优先于模型设置和角色默认值，优先级为：角色 > 模型 > 提供商 > 角色默认。

OpenAI 不受角色默认值影响：只有在提供商或模型上显式写 `cache_retention = "long"` 才会发送保留字段，Director 默认的 `long` 不会自动开启 OpenAI 的 2.5 倍写入选项。GPT-5.5 及更早的 `gpt-*` 模型发送 `prompt_cache_retention: "24h"`；GPT-5.6 及以后在 Responses 请求里发送 `prompt_cache_options: {"ttl": "12h"}`（写入价 2.5 倍）。其他提供商不受影响。

`cache_ttl_seconds`（正数，单位秒）可选，设置位置与优先级同 `cache_retention`。它告诉 Logox 这个网关的提示缓存大约保留多久，用来判断 Logox 的缓存是否已过期、是否可以免费折叠旧轮次（见[上下文管理](modules/context.md)）。设置了就以它为准。没有设置时，Anthropic 协议按 `cache_retention` 对应的时长计算；OpenAI 和其他服务不公开时长，视为未知，即永不过期，此时只在上下文达到高水位一半或越过水位线时折叠。设得比真实时长长，折叠只会晚一点发生；设得更短，则可能白付一次缓存写入。

```toml
[models."anthropic/claude-sonnet-5-5"]
cache_retention = "long"   # 该模型的所有角色都用 1 小时缓存，除非角色自己覆盖

[kernel]
cache_keepalive = true     # 默认开启
```

`cache_keepalive`（`[kernel]`，默认 `true`）在角色空闲、但必然会被再次唤醒时保活短缓存。必然唤醒只有两种情形：Director 的某个根任务下还有排队或运行中的派发工作（没有等待人类的交付），或某个角色在等待 `ask` 的回复且对方正在运行。等待人类时从不保活。保活重放该角色上一次请求（同样的工具、系统提示、消息和思考配置），只把 `max_tokens` 设为 1，不重试，在缓存生命周期的 90%（或剩余 10 秒，取较早者）时发出，直到角色被唤醒、工作结束或满 1 小时。只有 `missCost - warmCost >= $0.05` 才发送，价格未知则不保活；Anthropic `long`（1 小时缓存已覆盖等待）、预算式思考（`budget_tokens` 随 `max_tokens` 变化，无法重放）以及 OpenAI 默认保留都会跳过。保活请求不进入历史和时间线，用量以 `keepalive` 类别记入 `usage.jsonl`，`scripts/score-session.mjs` 为每个角色单列一行。

价格表里 `cache_write` 是 5 分钟写入价，1 小时写入价默认取输入价的 2 倍，可用 `cache_write_1h` 覆盖；用量中 `cache_creation.ephemeral_1h_input_tokens` 按 1 小时价计费，其余写入按 5 分钟价。

### 请求转储（调试）

设置环境变量 `LOGOX_DUMP_REQUESTS=1` 后，每个发给模型的请求体（经最终序列化器，与实际发送的字节一致）会写入项目数据目录下的 `state/sessions/<会话>/requests/<角色>/<序号>-<时间>.json`；缓存保活请求带 `-keepalive` 后缀。只写请求体，不含请求头、密钥或认证信息，但请求体本身包含对话内容，分享前请检查。

`node scripts/diff-requests.mjs <requests 目录或单个角色目录> [--context N] [--keepalive]` 对同一角色的相邻请求打印首个不同字节的偏移，以及两侧各约 200 个字符的上下文（默认跳过保活请求）。用它定位为什么前缀缓存没有命中：前缀应当逐字节不变，差异出现得越靠前，缓存损失越大。

### 缓存回归报告（请求指纹）

提示缓存只在请求前缀（工具、系统提示、再按顺序的消息）与上一次请求逐字节相同时才会命中。为了事后能解释一次未命中，每个发给模型的请求都会默认记录一条很小的“指纹”，追加到 `.logox/state/sessions/<会话>/requests/<角色>.fingerprints.jsonl`（`[kernel] request_fingerprints = false` 可关闭）。指纹只有短哈希、标签、估算 token 和缓存相关字段（`max_tokens`、思考配置、缓存保留与时长、是否带缓存键），不含任何消息文本、密钥或请求头；请求结束后另写一行 `result`（同一个 `id`），记录 `input` / `cacheRead` / `cacheWrite` / `output`，失败请求记录错误类别。写入是异步的，错误一律吞掉，不会拖慢或打断请求；每条记录约每个消息块 40 字节，长会话的指纹文件会随之增长，目前没有上限。

```bash
node scripts/cache-report.mjs <会话目录 | 项目目录 | 项目数据目录 | 旧版项目 .logox 目录> [--all] [--json]
```

报告按角色分段。每段先给出请求数、纯追加比例、缓存读取占输入的比例和各类未命中的数量，再给出各类别（工具、系统、用户、助手文本、思考回放、工具参数、按工具名的工具结果、图片、宿主消息）的平均 token 与最大请求；随后是相邻 `task` 请求的对比表（默认只列出前缀被破坏或未命中的行，`--all` 列出全部）：

- `kept`：新请求保留了上一次请求前缀块的数量，`kept/total`；`pure` 为 `yes` 表示新请求只是在末尾追加（缓存可以延续）。
- `first difference`：第一个不同的块，写作 `block <序号> <上次标签> -> <本次标签>`，序号 0 是工具列表，接着是系统块，再是消息块；标签来自 Logox 自己的类型化消息，例如 `tool:Read`、`context:reminder`、`context:task-state/ensemble`、`assistant+calls2`、`user+img1`。`tokens after` 是从该块起需要重新读取的估算 token。
- `cache`：该请求的 `cacheRead / input`。读取接近零（低于 5%，且输入至少 1024 token）才算未命中，并分四类：`prefix changed`（Logox 改了前缀字节，括号里是第一个被改的块的序号）、`fields changed`（前缀未变，但模型、协议、思考配置、缓存保留、时长、缓存键或工具披露方式变了，括号里列出字段）、`idle`（前缀与字段都没变，但距上一次请求的间隔超过那次请求记录的缓存生命周期）、`unexplained`（前缀与字段都没变且间隔很短，只能认为是服务端丢弃了缓存）。
- 只有改动点之前的估算 token 少于该请求输入的一半（即提示的大部分在改动点之后）时，才算 `prefix changed`。如果第一个不同的块只是上一次请求的最后一块、其后只有几百 token，它无法解释接近零的缓存读取：这时按“前缀未变”继续判为 `fields changed`、`idle` 或 `unexplained`，改动点仍显示在 `first difference` 列。
- `read stops at ~N tok`：缓存读取不为零，但不到保留前缀（按指纹块大小估算，至少 1024 token）的一半时标注，N 是实际读取量。读取量在保留前缀不断变长时保持不变，说明服务端只缓存到这个位置，问题在提供商而不在 Logox。`--json` 的每个 pair 同样带有 `keptTokens` 与 `readStopsAt`。

示例（合成数据）：

```text
[techne] 6 requests (task 6, keepalive 0)
  pure append 80% (4/5 pairs) | cache read 15% of input
  misses 4: prefix changed 1, idle 1, fields changed 1, unexplained 1
  time      kept  pure  first difference                                          tokens after  cache  miss class
  13:47:00  5/5   yes   -                                                         100           0%     unexplained (10s gap)
  13:47:10  3/6   no    block 3 msg#1 assistant+calls1 -> msg#1 context:reminder  400           0%     prefix changed (block 3)
  13:47:20  7/7   yes   -                                                         100           0%     fields changed (thinking)
  13:54:00  8/8   yes   -                                                         100           0%     idle (400s gap, lifetime 300s)
```

`scripts/score-session.mjs` 在 `[Cache]` 段用同一份数据为每个角色列出纯追加比例、缓存读取比例和各类未命中数；没有指纹文件的旧会话显示 `n/a`。需要对比实际字节时再用上面的请求转储。

```toml
[provider]
tool_discovery = "none" # 保守使用普通工具集
```

`.logox/tools.json` 可按角色设置工具的 `roles`、`loading` 和 `terminalVisibility`，项目级覆盖用户级。协议编码、渐进披露和缓存相关的细节见[上下文模块](modules/context.md#系统提示与工具披露)。

## 提交任务与角色

直接输入任务交给 Logox，也可以用 `@` 指定角色：

```text
@aletheia 查找这个问题的相关实现并核对原因
@techne 修改代码并运行相关测试
@kalon 整理这段说明，让它更容易阅读
```

在角色窗口里输入的普通内容交给当前角色。每个角色有独立的历史：**同一角色的任务串行，不同角色可以并发**。它们共享同一份项目文件，不是隔离的工作树。`/cast <task>` 把同一个任务同时交给三个内置角色。

`/ensemble` 打开角色总览（见下节）；`/model <actor>` 设置该角色的默认模型，未设置时继承会话模型。

**角色自己的思考档位**：角色（和 Automa）的专用模型可以带自己的思考档位，写法 `/model <actor> <model> [档位]`，例如 `/model techne gpt-5.5 high`（档位为 `auto/off/low/medium/high/max`，不在该模型支持范围内会报错）；也可以在选择器里选好档位后确认，选择器只列出该模型支持的档位，并以当前绑定的档位打开。不写档位就跟随会话档位（与以前相同）。设了档位后，该角色的请求、摘要（用自己的模型时）、`/ensemble` 与状态栏都显示并使用这个档位，会话里改档位不影响它；模型名本身带档位（如 `...-high`）时以名字为准，不会另存。已开始的任务保持开始时的档位（重启后也是）；任务降级到会话模型时改用会话档位。绑定文件（`actor-models.json`、`tool-models.json`、角色定义的 `defaultModel`）多了可选字段 `effort`，旧文件无需改动。在角色窗口里输入 `/model` 也是设置该角色的默认值。角色定义与技能覆盖见[角色模块](modules/actors.md)，单任务的模型确认与转用见[任务模型](modules/task-models.md)。

### 排队与插话

一条输入有三种去向：

| 方式 | 触发 | 行为 |
|---|---|---|
| 发送 | Enter | 目标（Logox，或当前聚焦的角色窗口）空闲时立即开始新一轮。目标正在运行时消息排队：它不写进时间线，而是显示在输入框上方的待发送列表（每条一行，行尾 `Queued · Send now  ×`），本轮结束后按顺序作为后续轮次送出并离开列表。斜杠命令和 `/skill` 展开不排队 |
| 立即发送（Send now） | 点击行尾 `Send now`，或输入框为空时按 Ctrl+T（发送最新一条） | 把该条待发送消息在目标下一个步骤边界（当前模型回复或当前工具批次结束之后、下一次模型请求之前）注入正在运行的一轮，并附一条静态提示，让模型知道这是工作中途收到的消息，可能改变方向。不会中止正在运行的工具。它随后作为该轮内带淡色 `· steered` 的用户行出现在时间线，并离开待发送列表 |
| 精确插话（Steer） | 有草稿时按 Ctrl+T | 把草稿直接在选中活动的下一次模型请求边界补充进去，页脚会写明目标；用于同一窗口有多个活动时指定其一，或目标正在等待回答时 |

待发送行的 `×` 把消息取回输入框（草稿非空则追加到末尾）。待发送列表只保存在当前进程内，退出或切换会话时未送出的消息不会保留。

引导消息写入对应角色的追加式账本（`source` 为 `steered`），恢复会话时仍显示为 `· steered` 行，模型看到的账本保留提示前缀。在 Logox 窗口里输入 `@角色 内容` 时，如果该角色正在运行，同样进入待发送列表（行首标 `→ 角色`），可对它 Send now。按 `Esc` 取消的语义不变，恢复到输入框的仍是原始请求，而不是引导消息。

精确插话的规则：

- 目标用 Ctrl+N 选择，可以选任务，也可以选属于该任务的工具或思考卡片；点击卡片同样会选中它所属的活动。没有显式选择时，如果窗口里恰好只有一个进行中的活动，就用它。
- 选择绑定到活动本身：目标结束后草稿保留在输入框，不会发给别的任务。
- 插话不会取消请求或进程，也不会回答待处理的提问，不能执行斜杠命令或 `@角色` 路由。命令和另行指派的任务请直接用 Enter。取消仍用 `Esc` 和角色的停止控制。

在 Logox 窗口里 `Esc` 分两级：第一次只停止 Logox 当前回合（若它派出的角色仍在工作，通知行会列出它们并提示再按一次 Esc）；约 2 秒内再按一次，停止 Logox 派出的全部角色、排队任务、Automa 工人和它们的后台 Shell 任务。你在某个角色窗口里亲自发起的任务不会被停止，角色窗口里的 `Esc` 仍只是返回 Logox。第一次 `Esc` 只有在你发出请求后 5 秒内、且这一回合还没有任何可见的助手输出（文字回复或工具卡片）时，才会把该请求放回空的输入框以便修改重发；时间更久或已有输出时只停止回合，输入框保持不变（输入框里已有草稿时也从不覆盖）。
- 时间线向上翻看时，底部居中浮出单行填充按钮 `↓ Latest  End`（离开底部后有新内容则写 `↓ 3 new  End`）；点击、`End` 或 `Enter`（输入框为空时）回到最新输出，Ctrl+E 仍可用。鼠标移上去按钮渐变高亮（设置里关闭动效则立即变色）。当前阅读的那轮对话的起点用户消息（角色窗口里是 Logox 的指派）滚出视口上方时，顶部会钉住一行 `❯ You  消息开头…  ↑ Jump`，悬停高亮，点击把该消息滚到时间线顶端；消息本身可见时不显示。
- **焦点区域**：任何时刻只有一个区域有焦点——输入框、时间线或侧栏（全屏页面、选择器打开时都不聚焦，关闭后回到原来的区域）。鼠标点哪里，哪里就获得焦点并渐亮（约 220 ms，关闭动效则立即切换），其余区域变暗：输入框的上下分隔线与提示符、时间线左侧的竖线、侧栏的边框。`Tab` / `Shift+Tab` 在输入框、时间线、待回答问题、停止按钮和侧栏之间轮换，`Esc` 回到输入框。时间线有焦点时 ↑/↓ 滚动、Home / End 跳到顶部 / 底部、`Ctrl+N` 选卡片。直接键入可见字符（或粘贴）总是回到输入框并输入，不会丢字；终端窗口失去焦点时当前区域整体变暗。
- 普通输入栏右侧的 `⛶` 可展开全屏草稿编辑，其中 Ctrl+Enter 与 Enter 同样发送，Ctrl+T 为 Send now / 精确插话，详见[终端操作](UI-SPEC.md)。

### Logox 的协调

Logox 向角色正式派工后，各角色的结果通过持久化的优先队列回到 Logox：失败和求助先于普通报告，同优先级按先后顺序。Logox 忙时，相关事件在它下一次请求前进入；空闲时会被唤醒。用户的显式停止不会被通知撤销。

- Logox 通过 `Actor` 的派工回执和报告、失败等事件了解团队；需要当前状态时用 `ListActors`（状态、任务标题、实时副标题、`owns`、正在运行的工具、近期的工具结果，所有角色都能调用）。角色的任务单会列出同批次的队友。命令执行完或角色自述状态，都不等于任务通过验收。
- 派工使用 `Actor` 工具：`title` 与 `prompt`（写给没看过对话的同事的完整说明）之外，可选 `owns`（可修改的路径，同时驱动文件归属提示）、`acceptance`（验收标准，随报告一并回到 Logox）和 `after`（要等的任务：同一次派工里某个任务的 `id`，或者之前某个任务的活动 ID；不接受角色名）。每个任务都是独立的活动：同一个角色可以在一次派工里有多个任务，组成一条多波次的流水线，比如 Kalon 画资产（`id` 为 `assets`）和 Techne 写引擎（`id` 为 `engine`）同时进行，Techne 的总装任务 `after: ["assets", "engine"]`，Kalon 的审查和 Aletheia 的验证再 `after` 总装；同一角色的任务按顺序一个个做，整条流水线是一个批次，全部结束后 Logox 才被唤醒一次。任务 `id` 只在被引用时需要写，用小写字母、数字和连字符，不能和角色名相同；写了角色名、重复的 id、未知引用或循环依赖，整次派工被拒绝并说明改法。`owns` 与 `acceptance` 会被渲染为角色任务中的一段 `Brief`。设置 `after` 后，运行时会让该任务排队（卡片显示 `Waiting on <角色>`），待所依赖的任务完成后，连同其报告一并交付；依赖失败或被停止时，该任务不会启动。同一次派工里，两个可能同时运行的任务（相互之间没有直接或经由其他任务的 `after` 关系）的 `owns` 重叠时，整次派工被拒绝、什么都不启动，结果说明是哪两个任务、哪个路径重叠，以及怎么改（用 `after` 排先后，或让每个文件只有一个负责人）；这项检查在简报检查之前，`"briefCheck": "skip"` 也跳不过。编辑文件本身从不需要拥有它。派工成功后，结果末尾可能附带提示（仅提醒，不拒绝）：新任务的 `owns` 和其他角色仍在进行的任务重叠、多角色派工中某角色缺少 `owns`、有 `owns` 却没有 `acceptance`。
- 每份交给 Logox 的报告（和失败记录）后面，运行时会追加一段“运行时记录”：该活动的 Edit/Write 和前台 Shell 命令改动了哪些文件、超出 `owns` 的文件、最近五条 Shell 命令及退出码、轮次由模型还是运行时关闭，以及 Logox 当初写的验收标准。它由账本直接生成，不调用模型，也不进入角色自己的记录；Logox 据此对照角色的自述，只复核两者留下疑问的部分。
- 你与某个角色的直接对话彼此独立，包括其本地失败。明确请求 Logox 协助时，可以让该对话进入协调，但不会移交整段对话或授予新权限。
- 重启后队列数据和历史保留，但被中断的工作不会自动重跑，工具也不会重放；绑定的插话不会重新指向别的目标，未完成的任务会显示为中断。协调消费失败时可能用稳定的事件 ID 重新投递，这不是"恰好一次"的执行语义。
- Logox 不做周期性轮询，没有读取次数上限，也不会自动判定任务停滞。派工结果本身会告诉 Logox：角色在后台工作，报告会自动唤醒它，期间不要预测结果、也不必重复检查；运行时不会因它重复读取而收回工具。由协调事件唤醒 Logox 的消息以一行“自动事件，并非人类消息”开头，不代表人类确认或批准了任何事。

投递与恢复的实现见[角色模块](modules/actors.md#消息与投递)。

### 计划与任务图：Plan 工具、幕与节目单

一个请求包含不止一块工作时，Director 用 `Plan` 工具为它建一份计划：最多三层的节点树（阶段、步骤、任务，编号 `1`、`1.2`、`1.2.3`），每个节点有负责人（角色 id，或 `automa`）、前置节点（`after`）、验收标准和证据。派遣时给 `Actor` 任务或 `Automa` 作业加 `node` 字段，节点的状态就跟着那份工作走：未派遣是 `pending`（前置未完成）或 `ready`，在做是 `running`，等审批、回答或排队是 `waiting`，做完是 `done`，失败或取消且没有更新的尝试是 `failed`。模型从不手写这些状态；只有 `accepted`（凭证据验收）和 `abandoned` 是写下来的。父节点的状态由子节点汇总。

- **谁能改什么**：Director 和你本人（GUI）可以改任何地方。角色只能在自己负责的节点之下增删改子步骤，负责人只能是自己或 `automa`；它不能验收自己的节点，只能验收自己节点的子节点，顶层节点由 Director 验收。`accept` 不带证据时，运行时从关联工作的记录里补（改过的文件、命令及退出码、Automa 作业的 `Finish` 证据）；没有关联工作又没给证据则被拒绝。被拒绝的操作都会写出修正办法，一次 `ops` 里的多个操作要么全部生效，要么全不生效。
- **计划文件**：每份计划是项目里的 `.logox/plans/<id>.md`，每次改动后原子写入，可以直接阅读和编辑（改标题、验收行，删节点，在列表里新写一行即可加节点）。节点编号、负责人、前置、关联和验收标记保存在行尾的 HTML 注释里，编辑可见文字时保持注释不动；勾选复选框等于你亲自验收，取消勾选等于重新打开。读不懂的行会作为备注保留，并只提示一次。运行时的改动与你同时在磁盘上做的编辑会按字段合并，不会互相覆盖。以前会话的计划可以在 `/plan` 的切换行里打开，只读，需要时重新激活。
- **看计划与任务图**：没有 `/tasks` 和 `/plan` 命令，也没有单独的任务视图：团队舞台（见下）是侧栏里唯一的视图，任务信息就在它上面。计划和任务是同一回事：计划只是“还没做的任务”。一个**幕（act）里的任务**是：这一幕里做出的计划的节点（可能还没有任何工作，状态 pending），加上每一次没有链接到任何计划节点的委派，二者自动并成一张图。没有链接的 Automa 作业或分身挂在派遣它的那个角色任务所在的节点下面（最多三层，更深的并入第三层节点）；没有链接的角色任务直接是这一幕的任务。合成的节点只读（界面上从不显示节点编号，编号只给模型和计划文件用），打开的是委派详情页（与下面“委派记录”相同）而不是计划节点页；Plan 工具、计划文件和 Director 收到的变化通知完全看不到它们。节点详情页：验收、证据、前置、关联工作；关联工作可直接打开对应的委派详情。点击舞台顶部的幕标题（或侧栏有焦点时按 `p`）打开**节目单（Programme）页**：按顺序列出各幕，每幕下面是它的任务（状态符号、标题、负责人、耗时或 running、`after <前置任务标题>`、`⑂`、`◦N`），舞台正在显示的那一幕前面有 `▸`；选中一幕的标题把舞台跳到那一幕，选中一个任务打开它的详情页（计划节点页或委派详情页，Esc 回到节目单）；最下面是 `Earlier plans · re-activate`：更早会话的计划，选中后成为本会话的计划（`PlanBoard.adopt()`；已有进行中的计划时先放弃它）。
- **幕（act）：一个自然的工作回合**：舞台一次只显示一幕。一幕从用户请求之后的第一次派遣（`Actor` 任务或 `Automa` 作业）开始，期间发生的一切都属于它：你在回合中途的插话和引导、`AskUserQuestion` 的提问与回答、Esc 中断以及随后的恢复、你在同事或后台工人还在跑的时候与 Director 的讨论、重新派遣、被并入的早先尝试。它在回合**自然结束**时关闭：Director 的一轮正常结束（`completed`，不是中断），并且这一幕里派出去的工作都已交回报告或结果（后台 Automa 作业和同事会让它保持打开，Director 对它们报告的跟进仍属同一幕；被中断的回合没有正常结束，所以不会关闭）。关闭之后的下一次派遣开启下一幕。只讨论、没有派遣的回合不开幕（它的帖子仍在动态里，幕与幕之间的帖子不属于任何一幕，舞台此时停在最后一幕的结束状态）。Director 可以在新回合的第一次派遣上写 `continueAct: true`（`Actor` 与 `Automa` 的可选字段，仅 Director 有效），表示它与上一幕是同一件事（追加修复、你在讨论里要求的下一步），于是重新打开上一幕而不是新开一幕。幕的标题是该幕里 Director 做出的计划的标题，没有计划时取这一幕第一次派遣的任务标题；进度是这一幕里已完成任务数除以任务总数。没有“回合关闭”记录的旧会话整场算一幕。
- **团队舞台侧栏**：有幕之后，时间线右侧出现一列团队舞台（见下“Team”）。默认宽度为终端的 34%（36 到 56 列）；用鼠标按住侧栏左边缘（边框那一列）左右拖动即可调整宽度，范围是 36 列到“终端宽度的 60%”与“给时间线留出 60 列”两者中较小的一个，拖动时边框变强调色；松开后宽度保存在 `~/.logox/ui-preferences.json` 的 `sidebarWidth`，下次启动沿用，终端变小时只是临时收窄、变大后恢复；双击边框恢复默认。侧栏像一个 GUI 小窗口：最上面是一条带页签的标题栏（见下“侧栏页签”），标题栏最右端的 `◨` 图标（类似编辑器的“切换辅助侧栏”按钮）点一下收起侧栏，与 `Ctrl+B`、`/sidebar hide` 相同；侧栏收起（或未停靠）时，时间线右侧让出两列，`◨` 图标单独占据第一行最右端的这两列（不会盖住任何文字），点它即可重新打开；标题栏页签、`×`、`+`、两处 `◨` 图标和团队舞台的角色卡片在鼠标悬停时有约 150 毫秒的渐变（`/settings` 关闭动画时立即切换）；覆盖面板形式同样有标题栏和这个图标，但不能拖动。终端不足 110 列时不会挤压时间线，此时侧栏以覆盖整屏的面板形式从右侧打开。计划变为 active 时自动出现（你手动隐藏过则不自动出现），计划完成或放弃时自动隐藏并提示 `Plan "…" is done · /team or Ctrl+B shows the team stage again`；你最后一次手动显示或隐藏的选择在本次会话内被记住。没有计划的会话不会自动打开侧栏（`/team`、`Ctrl+B` 或点击小标签就能看到）；`Ctrl+B` 在什么都没有时只提示 `Nothing has been planned or delegated in this session yet…`。有幕而侧栏隐藏时，侧栏收起时用右上角的 `◨` 图标、`Ctrl+B` 或 `/team` 打开。
  - **幕标题栏**：侧栏的第一行就是幕标题栏（没有页签）：`‹ Act 2 of 3 · 构思鹈鹕花样   ━━━━ 3/5 ›`，标签按状态着色，后面是细进度条和 `已完成/总数`（有失败时追加淡色的 ` · 1 failed`）。`‹` `›`（或键盘 `[` `]`）把回放点跳到上一幕或下一幕的第一个事件，没有可去的幕时变淡；点击标题（或按 `p`）打开节目单。幕跟随回放点：Live 时是最新事件所在的幕，往回翻就切到那个事件所在的幕；没有幕时标题栏写 `Team · no acts yet`，点击同样打开节目单（可在那里重新激活更早的计划）。
  - **卡片上的任务信息**：舞台只画当前这一幕里、到回放点为止出场的角色（上一幕的角色除非也参与这一幕，否则退场）。每张卡第一行是 `<符号> 名字`；第二行是这个角色在本幕当前的任务：任务标题（过长加 `…`）加右侧的 ` n/m`（该任务有子任务或工人时，已完成/总数），或等待原因（`waits techne`、`awaiting approval`），或任务标题加着状态色的 `done` / `failed`（它在本幕最后一个任务已结束）；第三行是它派出的工人（名字加状态）；有计划里分给它、还没开工的任务时，再有一行 `next: <标题>`（放不下的窄卡和紧凑形式不显示）。卡片仍是圆角、直角连线、总线、通道、脉冲，很多角色时折行或用紧凑形式。
  - **结果导向**：父节点从不因为某个子任务失败而显示失败：有子任务在运行或等待时它是 running 或 waiting，否则是 done（已验收则 accepted），失败只留在子任务和进度文字里。因额度、超时或中断而没有结果的委派，如果之后同一角色又接着做了（`resumeTaskId`，或同一 Director 一轮下该角色的下一次委派），它是“早先的尝试”：不单独成任务，工作并入后一个，详情页的 `Earlier attempts` 列出它们；Automa 工人被 `continue` 时 id 不变，本来就是同一个任务。没有后续的未完成委派保留为 `interrupted`（工作因额度、超时或中断停下而没有交出结果：是“未完成”，不是失败）。节目单里的状态符号：○ pending、◌ ready、● running、◐ waiting、◉ done、✓ accepted、✗ failed、⊘ interrupted、– abandoned。
  - **鼠标**：点击卡片选中它并把动态过滤到这个角色（再点清除），350 毫秒内再次点击打开角色页；幕标题栏、控制栏（`◀ ▶`、播放、进度条、速度）、`● Live` 和成员过滤都可点击、悬停变亮；滚轮在动态里一帖一帖地移动回放点，只滚动侧栏。
  - **键盘**：`Ctrl+B` 显示侧栏并把键盘交给它（再按一次隐藏；终端不足 110 列时打开或关闭覆盖面板）。选 Ctrl+B 是因为它不与任何现有按键冲突，也不会被终端的 XON/XOFF 截获（tmux 用户若把 Ctrl+B 设为前缀，可用 `/team` 或状态行小标签）。侧栏默认不抢键盘：只有按 `Ctrl+B`、`Tab` 轮到它、或点击侧栏内部时才获得焦点。获得焦点后：↑/↓/←/→ 在帖子间移动，`[` `]` 切换幕，Enter 打开帖子或所选卡片的角色页，`p` 打开节目单，Space 播放/暂停，`+` `-` 调速，`f` 成员过滤，PgUp/PgDn/Home/End 翻页，End 回到 Live，Esc 把键盘还给输入框；直接键入文字也会回到输入框并输入。输入框的草稿在侧栏聚焦时照常显示，只是没有光标。
- **Director 如何得知变化**：整份计划不会进入每次请求。角色的任务简报里只带它自己节点的路径和子树（`Plan context:`）；Director 只在别人改了计划（角色拆出子步骤、节点完成或失败）时收到一条只列出变化节点的更新；要看全貌时调用不带参数的 `Plan`。无界面运行（`-p --output json`）的报告里有 `plans`，列出本次运行涉及的计划及其各节点的当前状态。

### 委派记录：任务图里的委派与结束原因

委派记录就是任务图里的节点：在节目单里选中一个合成的任务，或在计划节点页里点关联工作，或在 Team 动态里双击一条与工作有关的帖子，打开一页只读的委派详情；每一次委派（Director 的一轮、角色的任务、Automa 工人）都有这样一页。没有 `/tasks` 和 `/plan`：舞台与节目单取代了它们。节点上写着状态和等待对象（`blocked by <角色>`、`awaiting approval (<工具>)`、`awaiting your answer`、`queued behind …`、`paused`）；详情页里还有结束原因（正常完成不加）、耗时，有价格时加费用（来自账本里已定价的 USD 轮次）。键盘、点击、悬停和滚轮与侧栏一致；Esc 关闭详情页。

详情页分三段：**Assignment**（所有者、标题、`owns`、验收标准）、**Status**（状态、`Stop reason`、一行诊断、等待对象、耗时、费用、批次、父任务；工人另有 id、路由和模型）和 **Result**（摘要、证据、`Not verified`、问题、完成时间，以及完整报告所在的引用：已有交付时是交付 id，否则是活动 id，可用 `ReadActor` 读取）。摘要优先取模型写的本轮摘要（轮次记录里的 `title`），没有时取报告去掉开头 `⏵ …` 状态行后的文字，再没有就取该任务最后说的话；`/tasks` 详情、侧栏提示和无头模式 JSON 的 `result.summary` 一致。被并入的早先尝试在详情页多一段 `Earlier attempts`。角色任务的页脚有 `o Open conversation`，直接切到该角色的窗口（与点击页脚的角色胶囊相同）；Automa 工人的页脚有 `t Worker transcript`，显示该工人在 `automa.jsonl` 里的简报、消息、调用和结果。页面是打开时的快照，不会自行刷新，需要最新状态时关闭后再从侧栏打开一次。悬停页脚里一个正在等审批的角色胶囊，提示行会写出 `Awaiting approval · <工具>`；等待依赖的角色写 `Waiting on <角色>`。

**侧栏页签**：侧栏的标题栏是一排页签，当前页签用加粗的强调色和下方的粗线标出，其余为灰色，鼠标悬停高亮。点击页签切换；多个页签同时打开时，每个页签带 `×` 可关闭（至少保留一个）；`+` 打开下一个尚未打开的页签；鼠标滚轮停在标题栏上循环切换页签；侧栏有键盘焦点时，数字键 `1`-`9` 选第 N 个页签，`w` 关闭当前页签。打开的页签集合和当前页签保存在 `~/.logox/ui-preferences.json` 的 `sidebarTabs` 与 `sidebarActive`，下次启动沿用。目前没有上下分屏：“多个窗口”就是多个页签。内置页签：
  - **Team**：团队舞台与动态（见下）。
  - **Changes**：本会话改过的文件，最近改动在前，每行是文件名、`+新增 −删除` 行数，第二行是目录、编辑次数和执行者；数据来自已完成的 Edit/Write 调用（不读文件；Write 覆盖旧文件的差异只在本进程记得旧内容时才准确，否则为近似值）。点击一行（或选中后按 Enter）以 Markdown 页面打开该文件的全部 diff。
  - **Usage**：Director 和各角色在本会话的 token 与费用（按 token 总量从多到少，价格未知时标 `~`），每行第二行是输入/输出/缓存和模型；点击一行打开该角色的窗口。滚轮每次滚三行，↑/↓/PgUp/PgDn/Home/End 移动选择，Esc 把键盘还给输入框。
  - **命令**：`/team` 打开并切到 Team 页签（已在 Team 页签且侧栏可见时再输入则隐藏）；`/sidebar [team|changes|usage] [show|hide|toggle]` 对任意页签做同样的事（默认切换：该页签已显示时再输入隐藏侧栏，否则打开并切到它）；不带页签的 `/sidebar` 只显示或隐藏侧栏。

**Team（团队舞台与动态）**：Team 页签是侧栏的第一个页签。`/team [sidebar] [show|hide|toggle]` 显示、隐藏或切换侧栏（默认切换：已经显示时再输入一次就隐藏）；没有幕的会话也能用 `/team` 或 `Ctrl+B`，什么都没发生时显示 `No team activity yet`。没有幕的会话也能用 `/team`，什么都没发生时显示 `No team activity yet`。Team 把团队的每一次派遣和每一次回复排成一条按时间的“在线工作群”：
  - **每条帖子两行**：第一行是发送者（符号和名字用角色颜色）、` → @接收者`、` · assign` 或状态词（`done` 绿、`blocked` 黄、`failed` 红、`interrupted` 灰）、右对齐的 `HH:MM`；第二行是一行淡色正文，超出宽度用 `…` 截断。等待（`waiting`）只有一行，工人派遣（`kalon ⇢ 3 workers`）的第二行列出作业（`◦` 工人、`⑂` 分身）。窄栏时先省略状态词，再把接收者折成 `@kalon +1`。没有任何背景色。
  - **事件来源**：你发给任何窗口的话（`you → @…`）；Director 的派遣（同一批合成一条 `assign`，正文是各任务标题）；角色之间和对 Director 的 `SendMessage` 与求助（收件方收到的那条，信封 `[Event …]`、`[Message from …]` 去掉；广播合成一条）；Automa 派遣（`workers`）和每个工人的结果（`worker → @派遣者 · done`）；角色交回的报告（`report`，正文是本轮摘要，去掉开头 `⏵` 状态行）；`after` 造成的等待和等你审批、回答的等待。这条流是纯投影，不另存：恢复的会话从自己的记录里重新得到它；没有时间戳的旧记录按记录顺序排在最近一条有时间的消息之后；通过 `after` 等过的等待只在前置任务当时确实还没结束时出现，等待审批 / 回答只在它还挂着时出现。
  - **选择与详情**：点击选中一条，双击或回车打开详情页：工作类帖子（派遣、报告、等待、工人）打开委派详情，消息和你自己的话打开完整正文（按 Markdown 排版，Esc 关闭）。点击名字（发送者或 `@接收者`）只看涉及该成员的帖子，再点同一个名字取消；底部右端的 `all members ▾` 打开成员选择小窗（点选、↑↓ 回车、Esc 关闭），`f` 也能打开。
  - **滚动与 Live**：滚轮、↑↓、←→、PgUp/PgDn、Home 逐条移动选择（视图跟随），舞台控制行写 `13/26 · +9m47s`（选中第几条 / 共几条 · 距第一条的时间），`◀ ▶` 可点击，逐条前后移动；有舞台时底部只留右对齐的成员筛选，没有舞台（侧栏不足 12 行）时底部才写 `◀ ▶   13 / 26 · +9m47s` 和筛选。`● Live` 表示跟随最新一条：新帖子追加时视图停在末尾；任何手动导航都离开 Live（显示 `○ Live`，不再自动移动），点击 `○ Live` 或按 End 回到 Live。
  - **舞台与回放**：帖子流上方是一幅会动的团队图，选中哪一条，图就停在那一条发生之后的样子（只画这一条所在的那一幕，幕与幕之间的帖子则停在上一幕的结束状态；纯投影：`src/runtime/team-stage.ts:stageAt`，不另存）。侧栏高度不小于 30 行且给帖子流留出至少 5 行时画完整舞台，更矮时收成两行（控制条加一行状态 `Working ✧ kalon ⊞ techne · Waiting ◎ aletheia · Done —`，放不下时先去掉符号再截断），低于 12 行不画。
    - **控制条**：`◀ ▶ ▶ Play  ━━●━━  13/26 · +9m47s  1×`。`◀ ▶` 逐条前后；`▶ Play` / `❚❚ Pause` 播放与暂停（在最后一条上播放会从第一条重新开始）；进度条点一下跳到对应位置，按住拖动连续滑动（指针拖到侧栏外也继续跟随，松开结束）；右端 `1×` 点击在 1× / 2× / 4× 之间轮换。播放时每 900 ms ÷ 倍速前进一条，播到最后一条自动切到 `● Live` 并停止。键盘（侧栏有焦点时）：Space 播放 / 暂停，←/→ 逐条，Home / End，`+` / `-` 加减速（不循环）。手动逐条、点进度条、拖动都是瞬间跳转，不播动画，并且会暂停播放。
    - **图里有什么**：顶部是 Logox 圆角卡片，上方有你的 `✓ you`（出现过你的话之后才显示）；各角色是下方一排等宽的圆角卡片（宽 11–16、间隔 3，按固定名册顺序 kalon、techne、aletheia，其余角色按字母序跟在后面，所以卡片不会因出场先后而跳位；只显示到当前这条为止出现过的角色）。窄栏或角色多时，卡片均匀折成多行并转为紧凑形（名字和状态符号合并成一行：`● 工作中 ◌ 等待 ✓ 完成 ✗ 失败 · 空闲`）。卡片第一行是 `<符号> 名字`，第二行是状态（`working` / `waiting` / `done` / `failed` / `idle`），只要有任何角色派过 Automa，卡片就多一行放它派出的工人：`◦ scout ✓  ◦ palette …  ⑂ sketch`（`…` 进行中、`✓` 完成、`✗` 失败，`⑂` 是分身；放不下时换成计数 `◦3 ✓2`）。工人暂时显示作业标题，作业带 `name` 字段时改显名字。
    - **连线**（直角框线字符，圆角只用于卡片）：Logox 的 assign 沿总线向下到卡片（`▼`），角色的报告向上回到 Logox（`▲`），你的话从 `✓ you` 向下进入 Logox；用过的线保持淡色，当前这一条是强调色，仍在等待的依赖是黄色虚线（`┄ ┆`）。**角色之间的消息走通道**：每张卡片底边正下方有一个端口，消息是通道行里发送者端口到接收者端口之间的一段，接收者一端带箭头（`╰──▶╯` / `╭◀──╯`），用发送者的颜色，当前这条是强调色（旁边可带 `msg` 标签）；每行卡片下最多 2 行通道，重叠的消息按“当前这条优先、其后新的优先”确定性地分配，放不下的不画；不同卡片行之间的消息沿发送者端口下到通道、再经最右一列的侧干线进入接收者那一行的通道。只画当前这条和最近 4 条事件里的消息，更早的整条淡出（次数保留在角色详情页）；总线向下一行的卡片经最左一列的干线。任何线都不会穿过卡片。
    - **动画**：当前这条因播放或 Live 来了新帖子而改变时，一个 `●` 脉冲沿这条线从发送者走向接收者（约 500 ms，用终端平面已有的动画帧节奏，结束即停；减少动效设置下不播）：你的话从 `you` 进入 Logox，工人结果进入派出它的卡片。侧栏以覆盖层（窄终端）打开时不播动画，静止显示。舞台不使用任何背景色，图的总高度在整个回放里固定（按最终状态预留）。
    - **当前这条**：舞台下方是当前帖子的卡片（`── #13  ⊞ techne → @logox · done ─── 08:32` 加一行正文，单击选中、双击打开详情），再往下是原来的帖子流，选中保持同步。
    - **卡片交互**：单击卡片选中它并把帖子流筛到该成员（再点同一张取消，与点击名字相同）；双击卡片，或选中后按回车，打开角色详情页：状态、当前任务（最近一次派给它的任务或消息）、它派出的工人（名字、标题、状态、耗时）、与每个对象收发消息的次数、最近的几条消息，页脚 `o Open conversation` 切到该角色自己的窗口。悬停卡片边框变亮，被选中 / 筛选的卡片边框是强调色。
  - 无头模式 JSON 的 `team` 是本次运行的这条流；会话中心（`SessionHub`）有 `teamEvents(id)` 和随之变化的 `teamRevision`。

**结束原因 `stopReason`**：一个值说明工作怎么结束，由运行时在一处写入，不依赖错误文字：

| 值 | 含义 |
|---|---|
| `completed` | 正常完成（Automa 工人交回 `done`、`blocked` 或 `denied` 也算它已完成，状态另行显示） |
| `cancelled_by_user` | 你按了 Esc / Ctrl+C |
| `cancelled_by_director` | Logox 用 `CancelActor` 停止 |
| `interrupted` | 进程崩溃或被强杀，重启后标记；也用于原因未知的取消 |
| `shutdown` | 正常退出时被停止 |
| `error` | 其他失败（含工人在 `Finish` 里报 `failed`） |
| `max_tokens` | 输出反复被长度上限截断 |
| `refusal` | 提供商拒绝了请求 |
| `stalled` | 模型什么也没交付，或 Automa 工人连续三轮不调用工具 |
| `dependency_unmet` | Automa 作业没有开始：它用 `after` 等待的作业没有以 `done` 结束（状态为 `skipped`） |

出错时还有一行 `diagnostic`（最多 300 个字符，已去掉密钥样式的内容）。结束原因写在活动、任务检查点、交给 Logox 的报告和失败通知里（报告里是 `Stop reason: <值>` 一行），Automa 结果块在不是 `completed` 时多一个 `stop="…"` 属性（`status` 仍是工人自己报的）。失败的恢复预算按结束原因归类（同样是 `max_tokens`，措辞不同也算同一类）。旧会话里的 `user`、`director_cancel` 等旧值照常读取；没有这个字段的记录显示为“完成/失败/中断”之一，不报错。

**限额与排队的说明**：Automa 一次派遣里有作业因为会话的 `max_running` 已满而排队时，结果开头多一行 `Queued <n> of <m> jobs: the session runs at most <max_running> workers at once.`（每次派遣只一行）。Logox 派工时某个角色还在做上一个任务，派工回执里每个排队的任务一行 `Queued: <标题> (<活动 id>) waits behind <角色>'s running task "<标题>" (<活动 id>); it starts when that ends.`。

**恢复时的定义检查**：任务开始时会记下角色定义的指纹（档案文本的哈希和绑定的模型）；Automa 工人则记下系统提示（合约加项目规则）、授权和模型。用 `resumeTask` 恢复角色任务，或用 `continue` 续跑工人时，运行时拿它与当前定义比较；不同就照常恢复，但在被恢复任务的第一条消息和回执里各加一行 `Note: <名字>'s definition changed since this work started (prompt, model, grant); it continues under the current definition.`，括号里只列出变了的部分。没有存下指纹的旧记录不做比较。

### Automa：角色的并行工人

角色（包括 Logox）可以用 `Automa` 工具一次派出最多 8 个无状态工人，处理可以并行的独立调查或修改（例如"各模块里是否都成立"、"把同一处改动应用到这几个文件"、只需要结论的长测试）。一两次调用就能完成的小事不用它。工人的原始输出不进入角色的上下文，角色只收到回执。

- **最小写法**：`{"jobs": [{"brief": "列出 parseConfig 的所有调用点"}]}`。只有 `brief` 必填；`title` 缺省取 brief 开头，`writes` 可选。同时接受 `tasks`、字符串数组、`task` 字段，旧字段 `files`（等同 `writes`）、`persistence`、`instance`，并忽略 `n/a`、`none`、`new` 这类占位值。已退役的 `preset`、`commands`、`read`、`output` 和其他未知字段会被忽略并在回执末尾附一条说明，不会让整个派遣失败。
- **工人默认能做什么**：读取派遣者能读的一切；可以运行 Shell 命令；可以在派遣者自己的草稿区子目录（`<tmp>/logox-scratchpad/<cwdHash>/<sessionId>/<派遣者>/`）里写临时脚本和笔记。所有读取和命令都以派遣者的名义经过权限引擎，按当前模式裁决，与派遣者自己调用完全一样（`auto` 模式下例行命令放行，有风险的进入复核或询问），所以工人永远不会超出派遣者的权限，也不存在按预设的命令白名单。
- **`writes`**：只读工作不需要写任何授权。需要修改工作区文件时，在作业上列出 `writes`（路径或 glob），工人只能改这些路径。`writes` 不能是整个工作区，作业之间不能重叠，也不能与同伴正在进行的任务或作业重叠；写入同伴持有的文件时该作业被拒绝并指明持有者，其余作业照常运行。指向工作区之外的条目会被丢弃并说明；指向派遣者草稿区的条目直接允许，不是错误。
- **路径比较**：每个路径在与范围比较之前先规范化（解析链接、Windows 8.3 短名与长名、Windows 上忽略大小写、统一斜杠），所以 `C:/Users/Administrator/...` 与 `C:\Users\ADMINI~1\...` 视为同一路径。
- **拒绝与重复调用**：只有两种情况会整体拒绝：`writes` 写成整个工作区，或作业之间的 `writes` 重叠；错误信息给出具体的修正办法，例如"只读工作不需要 `writes`，去掉它"。被拒绝后，完全相同的调用（规范化之后）会立即得到同样的回答，不再规划或运行。
- **回执**：每个工人按固定结构收尾：`Verdict`（结论，必须能由证据推出）、`Evidence`（`path:line`，或命令加关键输出）、`Not verified`（没有核实或做不到的部分），总计不超过 600 字，超出部分按整行截断并注明。回执紧凑地显示这三段，并附 `changed`（运行时对真实写入的测量，含增删行数，不采信工人自述；不包含 Shell 命令改动的文件）、`ran`（运行过的命令）和 `denied`（被拒绝的调用）。
- **工人怎么收尾**：用 `Finish` 交回结构化结果（状态 `done` / `blocked` / `failed`、摘要、证据、未验证项；`blocked` 时附上需要回答的问题），或者直接用不带工具调用的纯文本回复收尾：这段文字（最多 2000 字符）就是摘要，状态记为 `done`。`Finish` 的参数宽进：未知字段丢弃，超长内容截断，`blocked` 没写问题时用摘要当问题；只有状态无效或摘要为空才被拒绝并说明改法，连续两次被拒绝则作业以 `failed` 结束，不会无限重试。既没有工具调用也没有文字的回复会得到一次提醒，连续三次则以 `failed` 结束（`The worker stopped without a result.`）。
- **续跑工人**：每个作业派出时得到一个好读的 id：派遣者名字的首字母加该会话里的计数，例如 `T1`、`T2`（Techne）、`K1`（Kalon）、`L1`（Logox）；首字母无法取得时用 `A<n>`。id 写在回执的 `<automa-result id="T1" …>` 里，也显示在作业卡片上。作业以 `done`、`blocked` 或 `failed` 结束后，工人并不销毁，而是带着完整的上下文保持空闲，不需要 `keep`：派遣者用 `continue: "<id>"` 加新的 `brief`（例如回答 `blocked` 工人提出的问题，或让它按反馈继续改）续跑。续跑的工人沿用创建时的 `writes`、模型和系统提示，新的 brief 作为下一条用户消息送入，收尾方式不变，回执沿用同一个 id。`keep` 保留为兼容字段：写了也没有效果，回执里附 `keep is no longer needed: every finished worker can be continued.`。
- **工人的停放与结束**：空闲工人的上下文达到 64000 输入 token，或空闲满 10 分钟，会写到 `state/sessions/<sessionId>/subagents/automa/<activityId>/<id>.json`（原子写入）并从内存释放；`continue` 时从文件复活，超过 64000 的上下文照样可以续跑，只是回执会提醒 `Note: this worker's context is large; a fresh job with a short brief is cheaper.`。派遣者的任务（活动）结束时，它名下所有空闲和已停放的工人一并结束，文件随之删除；也可以用 `release: ["T2"]` 立刻结束。对已结束或不存在的 id 续跑会被拒绝：`Worker T2 is closed or unknown; dispatch a new job.`。进程重启后，仍未结束的任务里的工人不会被自动恢复，但如果它已停放到文件，仍可用 `continue` 复活；没有文件的 id 视为已结束。
- **工人名字（`name`，可选）**：作业上可以写一个短名字，方便之后续跑或引用：小写 kebab-case，1–24 个字符，匹配 `^[a-z][a-z0-9-]*$`（例如 `scout`、`palette`、`api-tests`），不能长得像 id（`t1`）。名字在同一派遣者的存活和已停放工人（以及仍在运行的后台作业）里必须唯一：重名会整次调用被拒绝，并给出修法（换一个名字，或 `continue` 那个已有的工人）；同一次调用里两个作业重名也一样；不同派遣者可以用同一个名字，被同一次调用 `release` 的工人名字立刻可用。分身也可以起名。凡是接受 id 的地方（`continue`、`after`、`wait`、`release`）都可以写名字，不分大小写，id 照常可用；续跑的工人沿用自己的名字（`continue` 作业上再写 `name` 会被忽略并附一句说明）。名字随工人一起存进停放文件，重启后仍可用名字续跑，没有名字的旧记录照常加载。名字显示在：回执 `<automa-result id="T1" name="scout" …>`、Automa 卡片的作业行（`T1 · scout · 标题`，窗口窄时先截标题，名字保留）、`/tasks` 委派详情的 Worker 行（`T1 · scout`）、任务图中该工人的节点（`scout · 标题`）、团队流和舞台（舞台用名字，没有名字用标题）和 `logox -p` 的 delegations JSON（`name`）。不起名的工人不会自动得到名字，仍显示 id 和标题。
- **作业之间的顺序（`after`）**：作业上的 `after`（最多 8 项）写它要等的作业：本次调用里的 id（`T1`，按调用顺序分配，所以派遣者可以提前写出）、1 起的位置（`"#2"`）、完全相同的 `title`，或本任务里还留着的、之前结果给过 id 的工人。没有 `after` 的作业立即开始（仍受 `max_running` 与 `parallel` 限制）；有 `after` 的作业等它点名的作业都以 `done` 结束才开始，开始时它的第一条消息在简报之后多一段 `Results of the jobs this one follows:`，里面是每个前置作业的 `<automa-result>`（摘要、证据、`Not verified`、`Changed`、`Ran`，没有 `Trust:` 行，也没有对话记录）。等待中的作业不占 `max_running` 名额，也不占 `parallel` 的位置，卡片和 `/tasks` 里显示为 `waiting`（`/tasks` 的 `blockedBy` 列出还没结束的前置作业）。前置作业以 `blocked`、`failed`、`cancelled` 或 `denied` 结束时，依赖它的作业（包括间接依赖）不会开始，状态为 `skipped`，结束原因 `dependency_unmet`，结果块写 `Not started: <id> ended <status>.`；跳过的作业没有工人，不能 `continue`。派遣者回答前置作业并续跑它之后，再派一次依赖它的作业即可（例如同一次调用里 `continue: "T1"` 加一个 `after: ["T1"]` 的新作业）。`writes` 的互不重叠只检查可能同时运行的作业：有 `after` 路径（任一方向、含间接）相连的作业按顺序执行，可以写同一批文件。引用不存在的作业、别的派遣者的工人、有歧义的标题、环（会写出环的路径，如 `T1 → T2 → T1`），或作业数超过 `max_per_dispatch`，整次调用被拒绝并给出修正办法；被拒绝的调用不消耗 id。默认的 `wait` 模式下工具在整张图都结束后才返回。
- **后台模式（`mode: "background"`）**：顶层 `mode` 为 `wait`（默认）或 `background`。后台模式下调用立即返回回执：每个作业一行 `<id> <title> · running|queued|waiting on <ids>`，再加一句 `Results arrive as messages while you keep working; you do not need to wait for them.`。每个作业的结果块作为一条消息送给派遣者，走与同伴消息相同的投递路径（派遣者忙时排到下一个步骤边界，不会打断正在运行的工具）；3 秒内先后结束的结果合并成一条（一次唤醒），`blocked` 的结果不等合并立即送出，因它而跳过的依赖作业与它一起报告；整次派遣已没有未结束的作业时，最后的结果也立即送出。派遣者没有别的事可做时不会为等待发模型请求：它的这一轮保持打开（后台作业还在运行、等待，或结果还没送到时不收尾），无请求地停放，直到下一条消息到达。`Automa({"wait": ["T3", "T5"]})`（调用里只有 `wait`）停放到这些作业都结束，并把它们的结果块作为工具结果返回，它们不再作为消息重复送出；未知 id 会被拒绝，只能等自己本任务的后台作业。取消派遣者的任务会取消它的后台作业，也不再投递结果；`release` 仍然结束留存的工人。卡片和 `/tasks` 里后台作业带 `background`，已结束的标明 `delivered` 或 `not delivered yet`；无界面运行（`-p`）在后台作业结束并送达之前不会判定为完成，JSON 报告里这些作业的 `delegations` 项多 `background` 与 `delivered`。
- **工人风格**：角色 `config.yaml` 的 `automa` 块定义风格（`styles`），例如 Techne 的 `scout`/`edit`、Aletheia 的 `scout`/`probe`、Kalon 的 `scout`/`variant`。风格只决定工人系统提示的口吻（`flavor`）、模型（`model`）和并发（`parallel`），不授予任何权限。运行时自动选择：默认用 `default_style`，作业带 `writes` 时用 `write_style`（如有）；模型也可以用 `style` 指名一个，但从不必须。`exclusive` 列出的命令前缀（如 `npm test`）在同一派遣的各作业之间一次只跑一个。旧的 `default_preset` / `presets` 写法仍可读取（权限字段被丢弃）。已安装到 `~/.logox/actors/` 的旧配置需要运行 `npm run sync:profiles`。
- **读取模型与代码模型**：工人用哪个模型由作业有没有 `writes` 授权这一确定的条件决定，而不是猜任务难不难。没有 `writes` 的作业用**读取模型**（存储键 `automa-read`），有 `writes` 的作业用**代码模型**（存储键 `automa`，也就是以前 `/model automa` 的选择，升级后它自然成为代码模型）。派遣者只需要记住一条：只读的作业不要给 `writes`，除非它必须修改文件。
- **模型优先级**：对应的绑定（读取或代码）> 风格 `model` > 角色 `automa.model` > 自动默认 > 会话模型。风格里的名称可以是 `provider/model`、完整模型 id，或当前服务商下的模型族（如 `haiku`）；当前账户没有该模型时自动使用下一级。
- **自动默认**：键未绑定时在派遣时决定，页面上显示为 `auto → <provider> / <model>`。读取模型是会话服务商里最便宜、可能支持工具调用的 T1 模型，代码模型是最便宜的 T2 模型（价格取自模型目录，没有价格的排在有价格的后面；明显不是对话模型的 id，如 embedding、语音、图像生成，会被排除）。服务商没有该档位时取最近的较低档，再取最近的较高档，但绝不高于会话模型自己的档位；都没有时用会话模型，这种情况不会报错。
- **`/model automa` 页**：三行。**Read model** 和 **Code model** 显示绑定的模型（`provider / model · T2 ◉`）或 `auto → <provider> / <model>`；回车打开选择器，第一项是 `Auto (cheapest T1)`（读取）或 `Auto (cheapest T2)`（代码），选它就清除绑定回到自动；以前的 “recommended” 推荐标记已取消，因为自动默认已经生效。**Vision fallback** 是视觉后备模型，存在 `automa-vision` 下，选择器只列能看图的模型外加 `None`；读取或代码模型不能看图而又没有后备时，这一行以警告色显示 `None · vision jobs will fail`。命令：`/model automa <model> [effort]` 设置代码模型，`/model automa inherit`（或 `auto`）清除它；`/model automa read <model> [effort]` 设置读取模型，`/model automa read auto` 清除它。
- **`vision: true`**：作业必须看图（截图、设计稿、图片文件）时在作业上写 `vision: true`。该作业按路由选出的模型能看图就用它，否则改用视觉后备；两者都不能看图时只拒绝这一个作业，信息为 `Job "<title>" needs a model that can see images. Choose a vision fallback under /model automa.`，同一次派遣的其他作业照常运行。派工书没有“档位”字段：派遣者不能按任务换模型，只能标 `vision` 或给不给 `writes`。回执的 `<automa-result … model="<provider>/<model>">` 记下该作业实际使用的模型；作业日志 `automa.jsonl` 的 `end` 事件除 `model` 外还有 `route`（`read`、`code` 或 `vision`）。
- **宽度与并发**：`[automa]` 有四个键（第四个 `max_forks_running` 见下一条“分身”）：`max_per_dispatch`（默认 16，范围 1–32）是一次派遣最多带几个作业，超出会被拒绝并说明怎么拆；`max_parallel`（旧键，默认 4，范围 1–32）是一次派遣里同时运行几个，风格的 `parallel` 和派遣时的 `parallel` 优先于它；`max_running`（默认 24，范围 1–64）是整个会话里所有派遣者的工人同时运行的上限（只算正在运行的，空闲和已停放的不算），超出的按顺序排队，卡片上显示 `queued`。一次派遣超过 3 个作业且系统提示相同时，先单独启动第一个，等它收到第一次模型回应（或失败）后再启动其余的，让支持前缀缓存的服务商能从缓存读取共享前缀。工人一轮里的只读调用（Read、Glob、Grep）像角色一样成组并行，每组最多 `[permissions] readonly_concurrency` 个，写入和命令仍按顺序。
- **分身（`fork: true`）**：作业上写 `fork: true`，这个作业就不再是只看简报的工人，而是**派遣者自己的一个副本**：它带着派遣者此刻的全部上下文（系统提示词、工具定义、全部历史，以及派遣它的那一轮）接着干，`brief` 只需说清“这一块”和不做什么。只有角色（含 Logox）能用，工人和分身里不能再用（会被拒绝并给出办法）。**什么时候用**：这一块需要派遣者的理解和判断（比如沿着刚讨论出的取舍实现一个难点），而重写简报会丢信息；搜索、批量机械修改、只要判断结果的长构建，还是派工人，便宜得多。**成本**：分身每一轮都要重读整段上下文，约为工人的十倍；缓存没有命中时还会成倍上涨，所以每个派遣者同时最多运行 `[automa] max_forks_running` 个分身（默认 3，范围 1–8），多出来的排队，结果开头写 `Queued <n> of <m> forks: you run at most <k> forks at once.`。**怎么工作**：分身的第一条请求和派遣者那一条请求逐字节相同（同一个系统提示词、同一组工具定义和顺序、同样的历史、同一个服务商对象、同一模型和思考档位、同一个缓存键），后面依次是那条含 `Automa` 调用的助手消息、固定结果 `Forked. Your part follows.` 和一条分身指令（含 `Title:`、简报、`Scope:`、`Acceptance:` 与授权，写法和工人相同），所以支持前缀缓存的服务商从缓存读取继承来的那部分。分身永远用派遣者自己的任务模型和思考档位，`/model automa` 与读/写路由对它无效；能不能看图跟随派遣者的模型。授权与工人一样：`writes` 在同时运行的作业之间互不重叠、有文件锁，读取和命令按派遣者的权限判断。分身不能派工、再分身、给队友发消息、改计划或向你提问，这些调用在执行时被拒绝（工具定义不变，否则缓存前缀会变）；它用 `Finish` 交回结果，派遣者的上下文只收到这份结果块（`<automa-result … kind="fork" … cache="94%">`，`cache` 是它第一次回应里输入有多少读自缓存）。派遣者的工具列表里没有 `Finish` 时，分身仍然按名字接受它的 `Finish` 调用；如果服务商或模型根本无法调用未声明的工具，分身用不带工具调用的纯文本回复收尾，这段文字当作摘要，结果里加一行说明。**成本提示**：第一次回应缓存读取不到 50% 时，结果块多一行 `Note: this fork's prefix was not served from cache (<n>%); a fresh worker with a short brief is cheaper.`；服务商不缓存前缀（如本地端点）时，派遣回执说一次 `Forks on <provider> are not cached; each costs a full read of your context. Prefer workers with a brief.`（分身仍然可用）。ChatGPT 账号路由只缓存同一会话里的纯追加，分身这种“同一前缀上的另一条分支”能否命中还没有实测。**其余和工人一样**：分身用 `T1` 这样的作业 id，可以用 `after` 排序、`mode: "background"` 后台运行并逐个送回结果、`node` 链接到计划节点，完成后留在架子上，可以用 `continue` 接着干（接着的是它自己的历史，请求前缀同样不变；重启后不能继续，需要重派）。费用以 `fork` 类别计入派遣者（`/usage` 的 Session 页签有 `Forks` 一块和 `By category` 里的 `Fork` 一行，无头模式 JSON 的 `usage.byCategory.fork`）。界面上分身不是角色：不出现在角色标签、`/ensemble` 或提及里；Automa 卡片上它的那一行用派遣者的符号加 `⑂` 代替工人的圆点，`/tasks` 里显示 `kind: fork`（无头模式 `delegations` 的 `kind` 为 `fork`），任务图侧栏里由分身承担的节点，负责人后面加 ` ⑂`。
- **服务商请求并发与共享冷却**：在 `[providers.<name>]` 下可写 `max_concurrent_requests`（1–256，默认不设，即不限制），限制该服务商同一时刻在飞的 HTTP 请求数，角色和工人共用这个额度。它只包住单次请求：请求发出前取得名额，响应流结束或失败时归还，不包住角色或工人的整段运行，所以派出再多代理也不会因为互相占着名额而卡死。任何一次请求失败并给出等待时间（`Retry-After` 或“Cooldown wait 27s”之类的文字）时，该服务商的所有后续请求（角色和工人）都等到冷却结束再发，单次冷却最长 120 秒；遇到 429/529 限流时还会自动降低并发。
- **记录**：完整过程写入 `state/sessions/<sessionId>/subagents/automa.jsonl`，费用计入派遣者，在其 `/usage` 中显示为 `automa` 类别。写入有快照，可用 `/undo` 回退。进程重启时未完成的作业标记为 `interrupted`，不会自动重放。
- **派遣前的简报检查**：Logox 用 `Actor` 一次派出两个或更多新任务，或者其中一个 `prompt` 超过 1500 个字符时，运行时在任何任务开始之前先跑一次**简报检查**：一个只读的 Automa 式工人，用上面的代码模型，只有 Read、Glob、Grep，读完所有任务的 `title`、`prompt`、`owns`、`acceptance`、`after` 和接收者名字，必要时打开简报提到的文件。`resumeTask`、`SendMessage` 的后续消息和单个短任务不检查。结果有三种：没有缺口，任务照常开始，`Actor` 的回执多一行 `Brief check: clear.`；发现会导致做错或白做的缺口（未定义的名字或格式、互相矛盾的简报、两个任务都指望对方提供的文件、无法检查的验收、只靠“如前所述”给出的目标），则**不启动任何任务**，`Actor` 返回（不是错误）`Brief check found gaps; nothing was dispatched. …` 和带编号的缺口清单，Logox 修正后再派；在 `Actor` 参数里写 `"briefCheck": "skip"` 则不检查，直接派遣，回执为 `Brief check: skipped.`。检查本身失败（服务商出错、工人失败）从不阻止派遣，回执写 `Brief check: failed (<原因>); dispatched without it.`。费用按 Automa 计入 Logox 的 `automa` 类别，派遣步骤在检查期间显示 `Checking briefs`。

## 会话、整理与回退

普通启动会恢复最近的正式会话。没有历史或执行 `/new` 时，先进入临时空白会话，首次提交任务才登记；只打开设置不会留下空白聊天记录。恢复会话只展示历史，不会自动续跑工具或重新发请求。会话被占用或已损坏时会报告原因，不会悄悄改选另一段历史。

| 命令 | 作用与边界 |
|---|---|
| `/new` | 新建临时空白会话 |
| `/resume [id]` | 打开会话列表，或恢复指定会话 |
| `/clear` | 清理当前显示，不删除模型历史 |
| `/compact` | 整理当前角色的有效上下文，保留原始账本；必要时调用汇总模型 |
| `/undo` | 撤销受支持的文件工具造成的近期修改，不覆盖你之后的手工改动 |
| `/rewind` | 回退有效对话分支和相应的文件快照；原始记录仍保留 |

会话列表中按 Ctrl+X 进入删除确认，默认取消。当前会话和被其他进程占用的会话不能删除；删除前内容会备份到项目数据目录的 `state/trash/`。

**Shell 写盘审计**：每条前台 Shell 命令执行前后，运行时各取一次工作区状态（git 仓库用 `git status` 加文件修改时间和大小，被 ignore 的文件不算；不是 git 仓库时遍历工作区，跳过 `node_modules`、`dist` 这类目录，超过 5000 个文件就不审计），对比出这条命令改动的文件。结果末尾多一行 `Files changed: …`，改到其他角色负责的文件时附越界提示；这些文件进入运行时记录（Changed 和超出 `owns`）和无界面模式的 `changedFiles`。同一时间段里别人用 Write/Edit 写的文件和 `.logox/` 下的文件会被排除；别人同时运行的 Shell 命令改的文件无法区分，会被算进来。后台命令不审计。

`/undo` 与 `/rewind` **不会回滚 Shell、MCP 或其他外部系统的副作用**。多文件恢复也不是操作系统事务，部分失败时需要按提示处理。上下文整理与存储边界见[上下文模块](modules/context.md)。

### 轮次记忆

每一轮正常结束时，角色在最终回复末尾写一个 `<synopsis title="…">…</synopsis>` 块，作为这一轮的记忆，供压缩、`/rewind`、`/resume` 和团队页使用。时间线把它折叠成一行 `▸ Synopsis · 标题`，点击展开；Logox 收到的报告、无界面模式的最终回复和模型之后的上下文都不包含它。模型漏写时，运行时追加一次请求只要它补写摘要块；仍然没有，就由运行时根据记录写一条。旧版本的 `[context] round_memory` 设置已退役，写了也会被忽略。

## 权限

`/permissions` 打开权限页：

- **模式行**：`←` `→`（或 Space / `m`）只改页内草稿并标记 `unsaved`，下方一行说明所选模式的实际后果；Enter 才保存并提示 “Permission mode set to …”，Esc 离开且不应用。
- **规则列表**：按作用域（`user` / `project` / `session`）分组，每条显示决定（`allow` 绿、`ask` 琥珀、`deny` 红）、工具、匹配模式、命中次数和最近命中时间。`↑` `↓` 选择，`d` 或 Del 删除（行内 `y / n` 确认），`a` 打开新增表单（决定、工具、模式、作用域；输入会先校验，shell 模式必须是静态词元前缀）。
- **This run**：本次运行的审批统计（审批次数、询问你的次数、审查模型次数、审查用的 token）。

权限模式是用户级选择，所有项目共用：在任何项目里切换一次，保存到 `~/.logox/permission-mode.json`，其他项目下次启动时沿用。启动时的优先级：用户级已保存的模式，其次旧版本留在项目权限规则文件（`permissions.json`，现位于项目数据目录）里的 `mode`（仅在用户级还没有值时读取，且不再写入），再其次配置文件的 `[permissions] mode`，最后是内置默认值 `auto`。目前没有命令行参数。两个同时运行的实例互不实时同步，切换在对方下次启动时生效。规则和允许列表仍按作用域保存（项目规则在项目数据目录的 `permissions.json`），只有模式移到了用户级。

也可以用 `/permissions mode [default|auto|creative]` 直接选择，或用 `/permissions add <session|project|user> <allow|ask|deny> <工具> <模式>`、`/permissions revoke <id>` 管理规则。

| 模式 | 默认行为 |
|---|---|
| `default` | 普通只读操作走安全快路，其余需要人工授权 |
| `auto`（默认） | 读取、工作区内的编辑与写入、常见开发命令（构建、测试、lint、项目内装依赖、`git status/diff/log/add/commit`、运行项目脚本）直接执行；只有真正有风险的操作（工作区外写入或删除、`curl`/`sudo` 一类无法确认影响的命令、内联代码执行、外部 MCP 调用等）交给审批模型，凭据与 `.git` 等危险类仍询问人工 |
| `creative` | 在显式拒绝和危险过滤之后，其他操作默认允许 |

没有保存过模式的项目（新安装）使用 `auto`；显式保存的模式永远优先。

### 审批卡

请求审批的卡片显示 `<角色符号> <名称> wants to run · <工具>` 与右侧的 `Awaiting approval`；Shell 以 `$ 命令` 展示，其他工具展示紧凑的路径或 URL，不显示原始 JSON。风险行 `▲ <原因>` 后面是当前模式（弱化）。选项与单键快捷键：

| 选项 | 键 |
|---|---|
| Allow once | `y` |
| Allow `<前缀>` for this session | `s` |
| Always allow `<前缀>` in this project | `a` |
| Deny and tell `<角色>` why… | `n`（打开单行说明，Enter 发送，Esc 返回；说明会随拒绝一起返回给模型） |

`↑` `↓` 选择、Enter 确认、Esc 稍后回答；鼠标单击选项即作答（Deny 先打开说明）。前缀取自静态词元前缀（如 `npm ci`），不可编辑；复合或动态命令、危险类没有可生效的规则，因此不提供会话/项目授权。

### 规则

规则有三种决定：`allow`、`ask`（即使模式或允许规则会放行也一定询问你）、`deny`。优先级与作用域无关：**`deny` > `ask` > `allow`**；`forbidden` 命令和 `creative` 对凭据的拒绝仍在其上。作用域有三层：`user`（`~/.logox/user-permissions.json`，所有项目共享）、`project`（项目数据目录的 `permissions.json`）、`session`（仅内存）。规则对所有角色一视同仁，不存在按角色的规则；Automa 的授权仍只收窄派遣者已有的权限。每条规则记录命中次数和最近命中时间（项目和用户规则会落盘，会话规则只在内存）。

项目规则绑定项目的真实路径，所以移动项目后不能把旧路径当作同一个安全身份。会话临时目录（scratchpad）内的操作自动放行；`ask` 规则同样适用于它。

`creative` 允许写运行目录，但凭据和 Git 内部文件仍有独立保护。项目外访问、符号链接和 Shell 的实际影响仍要经过入口检查；获准执行的进程拥有当前系统用户的真实能力。这是应用内的权限机制，**不是操作系统级沙箱**。

## 资源与扩展

- 规范：按目录加载 `LOGOX.md`、`AGENTS.md`，或你自备的 `CLAUDE.md`。
- 技能：内置库、用户 `.logox/skills/`、项目 `.logox/skills/` 按名称覆盖。支持递归的 Markdown、角色目录和 `agent.md` 分类路标，正文按需读取，模型也可以用 `Skill` 工具搜索和加载。`/skills` 列出可用技能。

- MCP：目前支持 stdio 子进程，首次使用时启动，调用要经过 schema 与权限检查。
- Hooks：观察事件并执行配置的命令。启用前请检查脚本，它们不是沙箱内的纯数据。

格式、覆盖规则和生命周期见[资源与扩展](modules/resources-and-extensions.md)。

## 浏览器验证与离线运行

默认提供本地 `playwright` MCP 服务，按需启动；不使用 `npx` 临时下载，也不连接远程浏览器。首次在有网络时执行：

```bash
npm run browser:install
```

服务依赖随 `npm ci` 安装，浏览器需要提前准备并保留其用户缓存。之后浏览器本身可以离线运行，但网页的 CDN、远程字体和接口，以及云端模型，仍各有网络需求。换机器或升级 Playwright 后，需要重新准备匹配的浏览器。

模型在同一个页面会话里导航、观察、点击、输入和截图。MCP 返回的图片直接进入视觉输入，只有返回图片文件路径时才需要 `Read`。导航或点击的结果有时只给快照文件链接，此时调用不带文件名的 `browser_snapshot` 即可直接拿到页面内容和当前元素引用。截图默认写入隔离的临时工作目录。多个角色同时验证时，应约定一位浏览器操作者，避免互相切换页面。

本地页面建议通过本机 HTTP 预览访问；默认不开放不受限制的 `file://` 和项目外文件访问。服务使用独立的临时浏览器上下文，不复用日常浏览器的登录资料，调用仍遵守 MCP 权限检查。

需要自定义浏览器时，可设置 Playwright 官方的 `PLAYWRIGHT_MCP_EXECUTABLE_PATH` 环境变量，或在 `[mcp.servers.playwright]` 中显式覆盖服务配置。关闭内置浏览器：

```toml
[mcp]
playwright = false
```

修改 MCP 配置后需要重启 Logox，`/reload` 不会重启服务。

## 主题页

`/theme` 打开一整页：左边是主题列表（内置主题在前，保持原有顺序，其后是 `~/.logox/themes/` 里的用户主题，标有 `· user`；已保存的主题行尾有 `✓`），右边是用同一份调色板画出的样例，样例下面是可读性检查。`/settings` 的 Appearance 分组里 `Theme` 一行打开的是同一页，Esc 或选定后回到设置页。

- **预览**：移动高亮（`↑`/`↓`、`Tab`、`PageUp`/`PageDown`、`Home`/`End`，鼠标悬停某一行，或在列表上滚轮）就会把该主题应用到整个界面，页面本身立刻换色；预览期间不写任何文件。样例区上滚轮只滚动样例。
- **背景填充**：按 `b` 或点击页脚 `b background: on` / `off` 可逐主题切换是否以 `bg` 铺满整个画布（深色主题默认透明，浅色主题默认铺满），立即预览；仅在选定后按主题保存到 `~/.logox/ui-preferences.json`。
- **选定**：Enter、空格或点击某一行，把主题及背景设置保存到 `~/.logox/ui-preferences.json` 并关闭，状态栏提示 `Theme set to <名称>`。
- **放弃**：Esc、页脚的 `Esc cancel`，以及任何不经选定的关闭方式（包括程序退出）都会按页面打开时的调色板快照与背景设置逐项还原，还原发生在 `CommandSurfaces` 的关闭路径里，不依赖按键处理。保存失败时页面保持打开并显示原因，预览仍在，之后 Esc 照常还原。
- **加载失败的主题文件**：列在列表末尾，标 `✗` 和原因，不能选中，光标和悬停都会跳过。每次打开页面都会重新读取主题文件，所以新增或修好的文件无需重启即可出现。
- **布局**：终端够宽（约 100 列）时左右两栏；较窄（约 50 列）时列表在上、样例在下；更窄或太矮时只显示列表（页面自己仍按高亮的主题着色）。调整终端大小会立即重排。
- **样例**：由一段固定的假会话经过真实的时间线构建器、工具卡片和 Edit 差异渲染器生成，所以不会和真实界面漂移；状态符号、思考档位、权限模式、选区、提问卡和输入框几个区域没有时间线对应物，直接按同样的调色板字段绘制。样例画在该主题的 `bg` 上，便于判断对比。

**可读性检查**：第一行是 `Legible`（全部达标）或 `<n> below threshold`，随后每对颜色一格 `名称 比值`，达标用 `success` 色，低于阈值用 `warning` 色。比值是 WCAG 对比度（1 到 21），显示时向下截断到两位小数，所以显示 `4.50` 就一定达标。

| 名称 | 前景 / 背景 | 阈值 |
|---|---|---|
| `text`、`muted` | `fg`、`muted` / `bg` | 4.5 |
| `text on card`、`muted on card` | `fg`、`muted` / `cardExpanded` | 4.5 |
| `selection` | `selectionFg` / `selectionBg` | 4.5 |
| `diff +`、`diff −` | `diffAdded` / `diffAddedBg`，`diffRemoved` / `diffRemovedBg` | 3.0 |
| `border` | `borderMuted` / `bg` | 3.0 |

随后列出容易混淆的语义色：在 `accent`、`user`、`success`、`warning`、`error`、`question`、`link` 中，色相相差不到 20 度的两种颜色各占一行，例如 `accent ≈ warning`（`warning` 色）。灰色没有色相，不参与。这是提示而不是错误：部分内置主题的 `border` 只有 1.8 到 2.7，因为边线本来就是弱化的装饰。

| | Default thinking | 当前模型的思考档位，与 `/effort` 同一个保存路径，可选项随模型而定 |
| | Default mode | 权限模式，与 `/permissions` 写同一个设置 |
| Pages | Status bar、Permissions、Models & pricing、Shortcuts | 回车或单击打开子页面，Esc 返回，设置页上的草稿保持不变。Models & pricing 是只读表：每个已配置的供应商下列出模型的窗口、最大输出、每百万 token 价格，以及价格来源（`config` 是你自己写的 `prices`，否则是内置目录的匹配度 `exact` / `alias` / `normalized` / `inferred` 加目录名）；网关镜像其他厂商时用 `[catalogs.<provider>]` 声明，见[模型表](modules/model-table.md)。Shortcuts 是只读的按键分组表，暂不支持改键 |

操作：↑↓（或 Tab）选择，←→ 改值，Space 翻转开关或前进一个选项，Enter 保存全部改动并关闭（通知行显示 `✓ Settings saved`；没有改动时 Enter 等同于关闭），`/` 搜索（按标签、说明和分组过滤，标题右侧显示 `匹配数/总数`，Enter 回到列表，Esc 清除过滤）。文本行按 Enter 进入编辑，再按 Enter 提交，Esc 放弃；页面行与文本行用 Ctrl+S 保存。标题 `Settings · N unsaved` 的 N 是与已保存值不同的行数（大于 0 时为警告色）。有未保存改动时按 Esc 会在页内询问 `Discard N unsaved changes?`，`y` 丢弃，`n` 或 Esc 继续编辑，两个选项都可以点击。

保存失败（例如偏好文件损坏）时页面和草稿保留，错误写在页脚，同时以 `✗` 进入通知行；已经保存成功的行不会重复保存，修复原因后再按 Enter 即可重试。界面偏好用带锁的原子写入，不会覆盖损坏的文件。

## 状态栏

### 角色总览 /ensemble

每个角色（Logox、Kalon、Techne、Aletheia，不含 Automa）一个标签页，标签与页面边线使用该角色的颜色。`←` `→` / `Tab` 或点击标签切换角色。每页是一张可滚动的页面（`↑` `↓`、`PgUp` `PgDn`、滚轮）：

- **参数**：模型（`<model> · <thinking>`，标明 `set for <Name>` 或 `follows session`；`m` 或点击打开 `/model <actor>`）、上下文（用真实窗口和水位写成一句话，例如 `keeps 0 rounds and 2 tool results · compacts at 84% (167k)`）、角色档案路径（项目层扩展用户层时标 `+ project` 并列出两处路径）。
- **Tools · N / Skills · N**：以 `›` 结尾的两行，`Enter` 或点击进入子页，`Esc` 返回。
- **This session**：仅当前会话的任务、工具调用、审批、Token 与费用。
- **提示词**：Persona、Execution、Collaboration、Memory priorities 完整渲染为 Markdown，各带文件名；项目层角色档案存在时，Persona 显示合并后的生效内容并标 `+ project`。

工具子页与 `src/tools` 目录同构：根层是该角色实际可用的核心工具（`名称  简述`），再是每个分类目录一行（`▸ coordination · 3`）和每个 MCP 服务一行（`▸ mcp:playwright · N`，工具清单在该服务首次被列出后才有）。`Enter` 进入目录（面包屑 `Tools › coordination`），再按 `Enter` 打开工具详情：模型实际看到的完整描述、参数表（名称、类型、必填、说明）以及角色、加载方式和可见性。技能子页按来源（Built-in / User / Project）和目录分组，详情页渲染技能文件并显示来源路径。

`e` 用外部编辑器打开当前视野内的文件（提示词所在文件，或技能文件）：先 `$VISUAL`，再 `$EDITOR`，否则用系统默认打开方式（`start` / `open` / `xdg-open`）；编辑从不发生在界面内，终端内编辑器（如 vim）不适用。资源没有文件监听，保存后运行 `/reload` 才会生效。页脚提示 `←→ actor · ↑↓ scroll · Enter open · m model · e edit · Esc back` 可逐项点击，窄屏按重要性丢弃，子页里只显示适用的提示。

`/statusbar` 打开状态栏编辑器，`/settings` 的 Pages 分组里的 Status bar 是同一个入口（Esc 回到设置页）。可以选择风格（Pipes：彩色字段加竖线和上下文仪表；Starship：彩色底段加 Powerline 连接符），并独立选择 theme / gruvbox / dracula 配色和上下文仪表宽度，开关各模块并调整显示顺序。默认显示角色、模型、思考档位、权限、上下文仪表和缓存命中率，Git 与费用需要手动打开。

页脚有两行：上面是状态行，下面是通知行。通知行平时显示弱化的按键提示；鼠标悬停在任一模块（含右侧的 Actor 胶囊）上时显示它的详情，例如上下文各类别的用量和压缩水位、模型窗口与价格；操作结果（保存、复制等）会以 ✓ / ▲ / ✗ 短暂占用这一行。点击模型、思考档位或权限模块分别打开 `/model`、`/effort`、`/permissions`。终端高度小于 8 行时只保留状态行。窄屏下按“角色 > 权限 > 上下文仪表 > 模型 > 缓存 > Git > 费用”的优先级整项取舍，不会出现被截断的半截文字。实时预览不写盘，Enter 保存，Esc 丢弃未保存的草稿。从 `/settings` 进入时，保存后停留在状态栏页，Esc 回到设置页；独立的 `/statusbar` 保存后会收起。

先安装带 Nerd Font 字形的等宽字体并在终端中选用，推荐 [Maple Mono NF CN](https://github.com/subframe7536/maple-font/releases)，也可以用任意 [Nerd Font](https://www.nerdfonts.com/font-downloads) 的 Mono 变体，例如 `JetBrainsMono NFM`。偏好保存在 `~/.logox/statusbar.json`，旧布局自动兼容。按键与布局细节见[终端操作](UI-SPEC.md)。

## 用量页

`/usage`（别名 `/cost`）把“本会话花了多少”和“套餐还剩多少”放在一页，页签可用鼠标点击，滚轮滚动；页面随用量增长自动刷新。

- **Session 页签**（默认）：会话总计（费用、输入/输出/缓存读/缓存写 token、缓存命中率 = 缓存读 ÷ 输入、墙钟时间、请求数；有模型没有价格时费用标为 partial 并列出无价格模型），然后按角色顺序（Director、各伙伴）各一块，`Automa` 单独一块并归到派遣它的角色名下（用量本来就记在派遣者的计量器里，类别 `automa`；角色块不重复计入它），再是按模型和按类别（task / summary / approval / automa / keepalive / anamnesis，只列出现过的）。
- **Plan 页签**：只在使用订阅账号（ChatGPT 账号、Copilot 等 OAuth 登录）时出现。LOGOX 目前不读取套餐额度或限流窗口，所以只显示本会话在该账号上的用量、API 等价费用估算，以及一行说明“额度与重置时间由该提供商未报告”，不编造数字。

数字全部来自同一套用量与价格函数（`src/context/usage.ts`、`src/context/cost.ts`）。`/status` 的用量页签只显示会话总计和 `Details: /usage`。

## Anamnesis：回顾与长期记忆

会话空闲时，后台角色 Anamnesis 做两件事，各以一张 Anamnesis 卡片显示在它发生的位置：

- **回顾（recap）**：空闲满 `recap_idle_minutes`（默认 5 分钟）且有新内容时，写一段给回来的你看的短笔记：第一行一句话说明进度，其后是 Done / Open / Next。只读，除了这张卡片什么都不改。
- **入梦（dream）**：空闲满 `dream_idle_minutes`（默认 30 分钟）且有未审阅的内容时，审阅这段对话，把值得长期保留的事实存成记忆记录，或删除已不成立的记录。没有新东西时自动入梦不留卡片。

“空闲”指没有任务在跑、没有待回答的提问、没有压缩或重载，且你一段时间没有输入、提交或结束任务。你一动手，正在进行的回顾或入梦立即中止并且什么都不写，下次空闲时重新开始。已审阅的位置按会话记在 `state/sessions/<sessionId>/anamnesis.json`，重启后不会重复审阅。

记忆是两个文件夹里的 Markdown 记录（带 YAML 头：`name`、`description`、`metadata.type`，类型为 `user`、`feedback`、`project`、`reference`）：项目的 `.logox/memory/` 与你所有项目共用的 `~/.logox/memory/`。`user` 类型总是存到用户文件夹；看起来像密钥的内容不会写入。每个会话开始时（以及 `/reload` 时）读取一次记录，列在每个角色系统提示的 Memory 段里，所以会话中途新存的记录要到下个会话或 `/reload` 才出现。你明确要求“记住某事”时，角色可直接写入这两个文件夹里的 `.md` 文件，无需审批；这两个文件夹以外的 `.logox` 内容仍受保护。

```toml
[anamnesis]
recap = true             # 自动回顾；false 只关闭自动触发，手动运行仍可用
dream = true             # 自动入梦
recap_idle_minutes = 5
dream_idle_minutes = 30
```

两个自动开关也可以保存为用户偏好（`~/.logox/anamnesis.json`），优先于配置文件。Anamnesis 的模型默认跟随 Director 当前选择（不改变思考档位）；也可以为它单独选定模型，选定的模型不可用时本次运行失败并提示，不会悄悄换别的模型。它的用量记在 `/usage` 的 `anamnesis` 类别下。

`/anamnesis recap` 和 `/anamnesis dream` 立即开始对应的运行（状态行提示 `Anamnesis is writing a recap.` 或 `Anamnesis is reviewing the session.`，结果显示在卡片上）；有任务在跑时会报错，参数写错时提示 `Usage: /anamnesis [recap|dream]`。输入 `/anamnesis` 打开 Anamnesis 页面，六行每行左边是名称、右边是当前值：

- **Recap now / Dream now**：Enter 或点击立即运行并关闭页面；运行中值显示 `Running…`。
- **Memory records**：值为本项目与用户级记录的数量。进入后每条记录占两行（名称加 `<类型> · <project|user>` 标记，下面是弱化的描述），项目记录在前；选中一条打开详情（描述、文件路径、可滚动的内容），按 `d` 或点击 `Delete record` 并确认后删除文件，Esc 返回列表。没有记录时列表给出提示。
- **Model**：跟随 Director 时显示 `Follows Logox (…)`；进入后与 `/ensemble` 相同的模型与思考档位选择器，第一项 `Follow Logox (default)` 取消专用模型。所选提供商已不存在时值以警告色显示 `· unavailable`。
- **Recap when idle / Dream when idle**：Enter 或点击切换自动触发（`On · after <n> min` / `Off`），保存为用户偏好，停留在页面上。

每一层都支持键盘与鼠标（点击选中、再点击确认，悬停高亮，滚轮移动），Esc 返回上一层，最外层再按 Esc 关闭。打开页面本身算一次提交，会中止正在进行的自动回顾或入梦。

### 无界面运行（headless）

评测脚本、CI 和批处理可以用 `-p` 把一个任务从头跑到尾，不渲染界面、不启用鼠标、不改终端标题、不响铃、不弹引导向导，Anamnesis 的自动回顾和做梦也关闭。

```bash
logox -p "给 src/add.ts 补上单元测试并跑通"                 # 只在 stdout 输出 Director 的最终回复
logox -p - < task.md                                       # 任务从标准输入读取
logox --task-file task.md --output json --permission-mode auto > result.json
logox -p "整理 README" --verbose --timeout 30 2> progress.log
```

| 参数 | 作用 |
|---|---|
| `-p`、`--print <任务>` | 运行一个任务；`-p -` 从标准输入读取 |
| `--task-file <路径>` | 从文件读取任务（与 `-p` 二选一） |
| `--output text\|json` | `text`（默认）：stdout 只有 Director 本次运行最后一轮的最终回复；`json`：stdout 只有一个 JSON 对象 |
| `--permission-mode default\|auto\|creative` | 只对本次运行生效，不会写入保存的权限模式 |
| `--timeout <分钟>` | 可选，无默认值。到点后像 Esc / Ctrl+C 一样取消所有工作，等它们收尾，输出状态 `timeout` 并以 2 退出。它是外部的墙钟保险，不是智能体循环里的轮数或时间上限 |
| `--verbose` | 进度写到 stderr，每个事件一行：`[mm:ss] <角色> · <标题> · <状态或工具名>`，绝不混入 stdout |
| `--session <id>`、`--resume`、`--provider`、`--model`、`--base-url`、`--auth-file` | 与界面模式相同 |

- **新会话**：不带 `--session` 和 `--resume` 时 headless 总是新建会话（界面模式会重开项目里最近的会话），所以同一项目里连续的两次运行互不污染。会话 ID 在启动时写到 stderr（`Session <id>`），`--output json` 时也是；会话照常保存在 `~/.logox/projects/<键>/`，`scripts/score-session.mjs`、`scripts/cache-report.mjs`、`scripts/automa-outcomes.mjs` 可以直接分析。
- **何时结束**：Director 的这一轮已收尾，并且会话里没有任何角色的活动或 Automa 任务处于排队、运行或等待状态（连续约 150 ms 没有变化）。派给同伴或 Automa 的工作会等到汇报回来、Director 处理完才算完。
- **没人能回答的交互**：需要询问用户的权限请求由权限引擎照常裁决，凡是会弹审批的一律拒绝，理由是 `Headless run: nobody can approve this. Use --permission-mode auto or creative to let it proceed.`；`AskUserQuestion` 等提问一律回答 `No user is available in this headless run. Decide yourself from the task and the code, and state your assumption.`；需要登录时立即失败（退出码 3，`No usable model: run logox interactively and /login first.`）。
- **Ctrl+C**（SIGINT）：取消、等待收尾、输出状态 `cancelled` 并以 2 退出；第二次 Ctrl+C 不再等待。

| 退出码 | 含义 |
|---|---|
| 0 | 完成 |
| 1 | 失败（Director 任务失败或不可恢复的错误） |
| 2 | 超时或被中断 |
| 3 | 启动错误（没有可用模型、参数错误、任务文件读不了、任务为空） |

`--output json` 的 stdout 是一行 JSON：


`delegations` 列出本次运行里的每一次委派（与节目单读同一份投影）：角色任务（`kind` 为 `actor`，`id` 是活动 id）和 Automa 工人（`kind` 为 `automa`，`id` 是 `T1` 这样的工人 id，`parentId` 是派遣它的活动）。`status` 是活动状态或工人状态，`stopReason` 取上文“结束原因”表里的值（没结束时为 `null`），`durationMs` 未知时为 `null`，`costUsd` 来自账本里已定价的 USD 轮次（工人和没有价格的记录为 `null`），`blockedBy` 是还没结束的 `after` 依赖，`result` 在结束后有 `summary` 与 `notVerified`，否则为 `null`；工人另有 `route` 和 `model`。没有委派时是 `[]`。

`status` 为 `completed`、`failed`、`cancelled`（SIGINT）或 `timeout`。`actors` 里每个角色的 `tasks` 是本次运行里它启动的任务数，`toolCalls` 是它的工具调用数。`usage` 只统计本次运行新增的记录（`inputTokens` 含缓存读写，与 `/usage` 一致，Automa 与摘要、审批调用计入派发者或所属角色）；价格未知或不是 USD 时 `costUsd` 为 `null`。`changedFiles` 是 Write、Edit 和前台 Shell 命令（含 Automa 工人）改动的文件，相对当前目录；后台命令（`run_in_background`、`ShellJob`）的改动不在其中。

## 数据位置与构建

| 位置 | 内容 |
|---|---|
| `~/.logox/` | 认证、自定义提供商、模型目录、角色模型绑定、状态栏偏好、首次引导状态、称呼（`user-profile.json`）及用户资源 |
| 项目 `.logox/` | 你会阅读、编辑或提交的内容：`config.toml`、`actors/`、`skills/`、`hooks/`、`commands/`、`bulletin.md`、`memory/`（Anamnesis 项目记忆）。Logox 自动写入的运行状态不再放在这里，新项目的 `.logox/` 里只会出现 `bulletin.md` |
| 项目数据目录 `~/.logox/projects/<键>/` | 自动写入的运行状态：`state/`（会话索引、原始账本、上下文检查点、用量、删除备份、模型偏好、Automa 停放的工人、请求指纹与转储、Anamnesis 水位）、`snapshots/`（`/undo` 与 `/rewind` 快照）、`permissions.json`（项目权限规则）、`demo/`（`--demo` 的记录）。`logox --doctor` 会打印当前项目的这个目录 |
| 系统临时目录的 `logox-scratchpad/` | 按项目与会话隔离的临时工作资料；每个角色（含 Director）在会话目录下有自己的子目录，互不覆盖，彼此仍可读取 |

**目录键**：项目的绝对路径（解析符号链接后）里，每个不是字母或数字的字符都换成 `-`。Windows 的 `G:\hz\codes\Logox` 得到 `G--hz-codes-Logox`，POSIX 的 `/home/a/b` 得到 `-home-a-b`。同一路径总是同一个目录，不同路径可能（极少）撞上同一个键，此时两个项目会共享数据，请避免。

**一次性迁移**：旧版本把运行状态写在项目的 `.logox/` 里。升级后第一次在某个项目启动时（在读取任何状态之前），Logox 会把 `state/`、`snapshots/`、`permissions.json` 和 `demo/` 移到项目数据目录：先复制，核对文件清单和字节数一致，再删除旧的；用跨进程锁保证两个 Logox 不会同时迁移同一个项目。成功后时间线里有一条 `Moved runtime state to <目标>.`。任何一步失败，会删掉复制到一半的目标，旧数据原样保留，本次运行继续使用旧位置，并提示 `Could not move runtime state to <目标>: <原因>. Using <旧位置> for now.`，下次启动会再试。如果两边都已有同名内容，只搬目标里没有的文件；冲突的文件留在原处，并提示 `Runtime state exists in both <旧> and <目标>; kept <目标>. Left in place: <n> entries.`。迁移后项目 `.logox/` 里的配置、角色、技能、hooks、bulletin 和 memory 不动。

不要把认证和运行目录提交到公共仓库。项目会话可能包含源码、工具输出和任务内容，保存或分享前请先检查。

`npm run build` 只生成 `dist` 并复制角色与技能分发资产，不改写用户 home。资源加载时会补入缺失的内置技能，并刷新内容与已知旧版本完全一致的浏览器技能；你改过的文件保持不变，旧版自定义的截图流程需要自行更新。角色的安装与迁移同样只更新已知且未修改的分发默认内容。
