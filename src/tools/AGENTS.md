# Module: Tools & Execution (`src/tools/`)

## 1. Scope
- **Owns**: Built-in tool registry and metadata (`registry.ts`, `catalog.ts`, `metadata.ts`), Zod parameter schemas and aliases, native tool disclosure (`discovery.ts`), tool-owned UI (`ui-registry.ts`), process tree lifecycle (`process.ts`), and `/undo` snapshots (`snapshots.ts`).
- **Does not own**: Permission evaluation ([`src/permissions/AGENTS.md`](../permissions/AGENTS.md)); actor-facing tool execution and ensemble state ([`src/actors/AGENTS.md`](../actors/AGENTS.md)); MCP transport and the Playwright server config (`src/extensions/`, no signpost; routed through the Start Here table); provider wire formats for disclosure ([`src/providers/AGENTS.md`](../providers/AGENTS.md)).
- **Design rationale**: [docs/modules/context.md](../../docs/modules/context.md) (tool disclosure); [docs/modules/resources-and-extensions.md](../../docs/modules/resources-and-extensions.md) (MCP and Playwright).

## 3. Common Changes
### Add a built-in tool
1. Create `<tier>/<Name>Tool/` (`core` tools sit directly under `src/tools/`; tiers are `protocol/`, `coordination/`, `orchestration/`). Model it on `GlobTool/`:
   - `<Name>Tool.ts`: a `z.strictObject` schema, the `execute<Name>()` function, and `export const metadata: ToolMetadataInput` (`name`, `category`, `roles`, `terminalVisibility`; optional `loading`, `description`, `readOnly`: set it only for a tool that merely observes, since the kernel reads it through `catalog.ts:isReadOnlyTool()` to keep valid calls of a read-only batch and to count the Automa streak; Read, Glob and Grep carry it).
   - `prompt.ts`: the `<NAME>_DESCRIPTION` string (see `GlobTool/prompt.ts`).
   - `UI.ts`: `export const UI = createToolUI([...])` naming the title parameters (see `GlobTool/UI.ts`); add `stageLabel` (`ui-types.ts:ToolUI`, built with `ui-format.ts:stageText`) for the fallback activity label such as `Reading src/a.ts`, which is display only.
   - Optional `diagnostic.ts`, registered in `diagnostics.ts:diagnosticHandlers`.
2. Metadata defaults: `category: 'core'` implies `loading: 'eager'`; any other category defaults to `deferred`. Eager tools carry their full contract; deferred ones show one directory line (`description`) until `LoadTools`. To turn a tool off, give it empty `roles`, here or in `.logox/tools.json`. `roles` is `'all' | 'director' | 'actors' | string[]`; `terminalVisibility` is `'card' | 'notice' | 'silent'`.
3. Register the schema and description in `index.ts`: import them, add to `schemas` and `descriptions` (typed `Record<ToolName, string>`, so a missing entry fails typecheck), and add to the re-export block.
4. Register the metadata in `catalog.ts:builtinToolRegistrations()`: import `metadata as metaN` and append it to the array. The JSON-schema definition is derived from `schemas` and `descriptions`; only `SendMessage` is special-cased.
5. Add the canonical name plus lowercase and snake_case spellings to `types.ts:toolAliases`. Without them `canonicalToolName()` rejects the tool.
6. Add `UI` to `ui-registry.ts:toolUIs`.
7. Wire execution:
   - Tool that touches files or the shell: add a branch in `index.ts:Tools.execute()` after the permission block, and extend its `effect` computation if the tool is read-only.
   - Tool that needs ensemble state (the `coordination/` and `orchestration/` tools): add the name to `src/actors/services.ts:serviceTools` and a branch in `ActorServices.execute()`.
- Tests: `tests/tool-ui.test.ts` (iterates `schemas`; needs a UI entry), `tests/tools-registry.test.ts`, `tests/tools-claude-alignment.test.ts`; add a `tests/<name>-tool.test.ts` for execution.

### Give a tool a rendered card body
1. In `<Name>Tool/UI.ts` export a `<name>View(args, result)` returning a `ToolView` (`src/tui/timeline/tool-card.ts`): `summary` pieces only when they add information the title lacks, `body.lines` (`ToolLine` rows, built with the helpers in `src/tui/timeline/tool-code.ts` and `src/tools/GlobTool/UI.ts:pathSegments`), an `empty` line for no results, `tail: true` for output that reads from the end.
2. Render with `renderToolCard(context, {title: cardTitle(context, call), view})`; the shared code owns the 12-line cap, the `… N more lines` expander, failures and the header. Colours come from palette tokens (`path`, `highlight`, `link`, `syntax*`).
3. Data the UI needs but the result text lacks comes from a bounded side record or the call arguments, never from changing what the model sees (`WriteTool/record.ts:recordWrite` keeps the previous file text for the card).
- Tests: `tests/tool-card.test.ts`, `tests/tool-views.test.ts`

### Add a tool category / tier
1. Create the directory `src/tools/<category>/` (category names are directory paths; `metadata.ts:toolCategorySchema` allows nested paths).
2. Add `<category>: <one-line English description>` to the frontmatter `categories:` of this file. That is the only runtime source of descriptions; no formatter code changes.
3. Set `category: '<category>'` in each tool's metadata. Non-`core` categories default to deferred and appear in the LoadTools directory under `<category>/`.
- Tests: `tests/tools-taxonomy.test.ts` (new categories and the packaged signpost), `tests/tools-registry.test.ts`.

### Change a model-facing parameter
1. Edit the schema in `<Name>Tool.ts` (see `ReadTool/ReadTool.ts` for the pattern). Use Claude Code names (`file_path`, `old_string`, `new_string`, `head_limit`).
2. Never add `.default()` to a model-facing field; use `.optional()` and apply the default in `execute<Name>()`. Zod 4 lists defaulted fields as `required` in `z.toJSONSchema`, which forces the model to send them.
3. To keep an old name working, wrap the schema as `z.preprocess(value => normalizeAliases(value, {old: 'new'}), schema)` as in `EditTool/EditTool.ts`. The canonical key wins when both are present; the strict object then rejects any name that is neither.
4. If the path argument changes, update `aliases.ts:filePathOf()`, which `Tools.execute()` uses to build the permission target.
5. Update the description in `prompt.ts` and the title keys in `UI.ts`.
- Tests: `tests/tool-parameter-alignment.test.ts` (required lists, alias parsing), `tests/tool-contract-accuracy.test.ts` (description matches behavior).

## 4. Hard Boundaries
- **Model-facing fields never use `.default()`**: defaulted fields become `required` in the JSON schema. Partially enforced: `tests/tool-parameter-alignment.test.ts` asserts the `required` list of the core tools; other tools are *Unenforced*.
- **Legacy parameter names only through `normalizeAliases()`**: `path`, `old_text`, `new_text`, Grep `limit` are accepted but not exposed to the model, and are scheduled for removal. Enforced by `tests/tool-parameter-alignment.test.ts`.
- **Background jobs belong to one activity**: `Shell` `run_in_background` registers a detached job in `process.ts` (not in the foreground registry, so peer interrupts do not kill it); `src/actors/ensemble.ts` calls `process.ts:killBackgroundJobs()` when the owning activity settles and on `close()`. `ShellJob` reads output since the last read or stops the job; Automa workers are refused `run_in_background` in `index.ts:Tools.execute()`. Enforced by `tests/tool-shell-background.test.ts`.
- **Built-in names are PascalCase and resolve through `toolAliases`**: Enforced by `tests/tools-claude-alignment.test.ts`.
- **Write refuses wholesale rewrites of large files**: an existing file over 20 KB or 400 lines is rejected with a static notice pointing to Edit unless the call sets `overwrite: true`, and the refused content is saved under the caller's scratchpad (a rejected-writes subdirectory) with the path in the refusal; new and small files are unaffected (`WriteTool/WriteTool.ts:executeWrite`, `WriteTool/prompt.ts:WRITE_LARGE_FILE_NOTICE`). Enforced by `tests/tool-write-guard.test.ts`.
- **Playwright output stays in the actor scratchpad**: `Mcp.execute()` rewrites a relative `filename` argument of the `playwright` server into the calling actor's scratchpad (`extensions/playwright.ts:scratchOutputArguments`; absolute names stay as the model chose) and each actor's browser starts with `--output-dir` set to that directory (`extensions/playwright.ts:withOutputDir`), so screenshots never land in the project root. Enforced by `tests/playwright-browser.test.ts`.
- **Scratchpad is per actor**: each actor writes under `<session scratchpad>/<actorId>/` and offloaded output lands in that actor's `tool-results/` and tool-result images in its images directory (`src/kernel/scratchpad.ts:getActorScratchpadDir`, `src/kernel/scratchpad.ts:settleToolResults`, which also caps one turn's parallel results at `TURN_TOOL_RESULTS_LIMIT`); the permission engine still allows the whole session tree. Enforced by `tests/tool-scratchpad.test.ts`, `tests/image-history.test.ts`.
- **MCP text results collapse runs of 3 or more identical lines to `line (×N)`, and schema failures name their cause** (`src/extensions/mcp.ts:collapseRepeatedLines`, `zodCause`). Enforced by `tests/extensions.test.ts`.
- **Edit/Write overreach note is advisory**: `index.ts:Tools.withOverreachNote()` still runs the edit and appends one line when `ownership.ts:overreach()` finds another actor's active `ownedFiles`; wired by `Tools.setActivityProbe()` in `application.ts`. Enforced by `tests/tool-ownership.test.ts`.
- **Automa input is forgiving, the grant is not**: the model-facing shape is `{context?, jobs: [{brief, scope, title?, acceptance?, writes?}]}` plus rare `vision`/`keep`/`continue`/`release`/`style`/`parallel`. `AutomaTool.ts:normalizeAutomaInput()` maps `tasks`/strings/`task`, `files` to `writes`, derives `title`, reads a missing or unknown `scope` as `bounded` with the note `scope was missing; treated as bounded.`, drops placeholders ("n/a", "none", a `default` style) and drops retired or unknown fields (`read`, `commands`, `output`, `preset`) with a note; `grant.ts:planDispatch()` normalises every `writes` entry and picks the worker style. None of this widens a grant. Enforced by `tests/automa-tool.test.ts`.
- **A peer's change reaches the actor as a note, and shown hunks count as seen**: `file-views.ts:FileViews` (owned by `snapshots.ts:Snapshots.views`) keeps, per actor and file, what the actor last saw (a Read or its own write) and which changed line ranges it was never shown. `Tools.fileChanges()` builds one note per request for everything that changed since (other actors' and workers' writes named, outside changes unnamed; hunks only while at most `NOTE_LINE_BUDGET` changed lines, else ranges to Read) and delivering it marks shown hunks as seen. `EditTool.ts:executeEdit()` refuses a match that overlaps an unseen range and names only those ranges; any other Edit with a unique match proceeds under the per-file lock. A full `Write` over a file a peer changed still needs a fresh Read (`snapshots.ts:Snapshots.stalePeerWriter()`; a note does not satisfy it). Views are memory-only and `Tools.forgetFileViews()` runs on every fold or compaction, so a restored or folded actor gets no notes and today's rules. Enforced by `tests/tool-file-views.test.ts`, `tests/edit-tool.test.ts`.
- **A new file over about 300 lines is written as a skeleton plus Edits**: `WriteTool/prompt.ts:WRITE_DESCRIPTION` says so, because a reply that hits the output cap loses its cut-off tool call whole (`prompts/runtime/recovery.ts:executionRecoveryInstruction()` tells the model to redo it smaller, never to continue it). Enforced by `tests/tool-file-views.test.ts`.
- **Every Automa tool call re-enters `Tools.execute()` as its principal**: no worker path calls an `execute<Name>()` directly, so the principal's tool access, permission modes, rules and path dangers apply unchanged; worker reads do not satisfy the principal's read guard. Enforced by `tests/automa-tool.test.ts`.
- **Workers may write the dispatcher's own scratchpad subdirectory and nothing else beyond `writes`**: `grant.ts:pathDenial()` lets Edit/Write through only inside `getActorScratchpadDir()` of the dispatching actor (never another actor's subdirectory) or inside the job's `writes`; the call still passes the permission engine under the dispatcher's name. Every path is canonicalised before comparison (`paths.ts:canonicalPath()`: realpath, Windows 8.3 short names, case-insensitive on Windows, slash normalised), so `C:/Users/Administrator/...` and `ADMINI~1` spellings compare equal; a `writes` entry pointing into the scratchpad is accepted silently. Enforced by `tests/automa-tool.test.ts`.
- **A worker has the dispatcher's read access and Shell, and only `writes` widen workspace writes**: reads, searches and Shell commands carry no per-job allowlist and are judged by the permission engine exactly as the dispatcher's own call in the current mode (routine commands pass, risky ones go to review or ask), so a worker can never exceed the dispatcher; only Edit/Write outside the scratchpad and `writes` are refused before the engine, with no approval card. Workers never get Automa, Actor, SendMessage, CraftActor, CancelActor or AskUserQuestion. `writes` cannot be the whole workspace, must be disjoint across jobs, and cannot overlap a peer's active assignment or running job. Fixable mistakes (outside-workspace entries, unknown style, retired fields) are dropped with a note; a refused dispatch states its exact fix, and an identical call after a refusal is answered at once without running (`index.ts:Tools.runAutoma()`). Enforced by `tests/automa-tool.test.ts`.
- **A worker runs on the kernel's own parts and ends with a result: `Finish` or a plain reply**: `src/kernel/worker-run.ts:runWorker()` is the loop (provider retries on the kernel schedule `src/kernel/model-turn.ts:retryDelay()` so a stated `retryAfterMs` is waited out, request projection and image placeholders, per-turn offload into the worker's own `tool-results/` through `src/kernel/scratchpad.ts:settleToolResults()`, `src/kernel/repeat-guard.ts:RepeatGuard`, unique call ids); it has no ledger, no store activity and no round memory. `Finish` (`finish.ts:finishSchema`: `status`, `summary`, `evidence`, `notVerified`, `question` only for `blocked`, required there and dropped beside any other status by `finish.ts:parseFinish()` so a filler value cannot loop the job) is offered to workers only, never reaches `Tools.execute()`, and is refused with its fix when invalid or when it shares a batch with other calls. A complete reply with text and no tool call ends the job as `done` with that text (up to 2,000 characters) as the summary (`src/kernel/worker-run.ts:WorkerTerminal.plain`); a turn with neither gets one transient `reminder` and the job stays open, and the third such turn in a row ends it as `failed` with `The worker stopped without a result.` (a stall rule, never a budget). `Finish` arguments are read leniently (`finish.ts:parseFinish()`: unknown fields dropped, over-long text cut, `blocked` without a question asks its summary, a question beside another status dropped); only an unusable status or an empty summary is refused, and a second refusal in a row ends the job as `failed` with that refusal (`src/kernel/worker-run.ts:REFUSED_TERMINAL_LIMIT`). `blocked` is not a failure and can be continued with the answer. Enforced by `tests/automa-tool.test.ts`.
- **A worker's system prompt is the same bytes for every job of a dispatch that shares a style**: `AutomaTool.ts:workerSystem()` = `AUTOMA_SYSTEM_PROMPT`, then the project rules in the exact block actors render (`src/prompts/boundary.ts:projectRulesSection()`), then `# Shared context` (the `context` field), then the style flavour; no persona, collaboration or memory section. Job specifics (brief, `Scope:` gloss, `Acceptance:`, grant) live in the user message (`AutomaTool.ts:jobMessage()`). Enforced by `tests/automa-tool.test.ts`.
- **The result block is generated by the runtime, and a `Changed` line is measured at the write, never self-reported**: `AutomaTool.ts:resultBlock()` writes `<automa-result id title status took model>` with Summary, Evidence, Not verified, Question (blocked only), Acceptance, `Changed (measured)`, `Ran` (exit codes read from the command's own result), Denied and Kept; worker text has any `automa-result` tag escaped; one `Trust:` line follows the last block of a dispatch. `Changed` does not cover files changed by Shell commands (*Unenforced* gap, stated in the tool description). The journal `end` event carries `model`, `scope`, `status`, `vision` (summarised by `scripts/automa-outcomes.mjs`). Enforced by `tests/automa-tool.test.ts`.
- **A result block says how a job ended, and a dispatch says when the session limit made jobs wait**: `AutomaTool.ts:resultBlock()` adds `stop="<reason>"` after `status` only when the outcome (`src/runtime/stop-reason.ts:stopReasonFor()`: finished `done`/`blocked`/`denied` is `completed`, a stall is `stalled`, a thrown failure is mapped from the error, a cancelled job takes the dispatcher's stop cause) is not `completed`; the swarm state of each job also carries `route`, `model`, `stopReason` and the `Finish` fields for the delegation record (`src/runtime/delegations.ts`). A dispatch in which some jobs had to wait for a `max_running` slot (`src/kernel/semaphore.ts:Semaphore` (`saturated`) read as each job asks) starts its result with one `Queued <n> of <m> jobs: the session runs at most <max_running> workers at once.` line (`orchestration/AutomaTool/prompt.ts:queuedJobsLine`), never one per job. A worker stores a definition fingerprint (project-rules hash `AutomaTool.ts:workerPromptHash()`, grant, model; `workers.ts:IdleWorker.fingerprint`, also in the parked file) and a `continue` after a change adds the `Note: <id>'s definition changed since this work started (...)` line to the brief and to the block; a continued worker resolves its model again, so it runs on the current one. Enforced by `tests/task-automa-record.test.ts`, `tests/automa-tool.test.ts`.
- **Every finished worker stays addressable until its task ends**: each job gets a readable id when dispatched (`workers.ts:WorkerShelf.allocate()`: the dispatcher's first letter and a per-session counter, `A` for an owner without a letter) that `<automa-result id>` and the card carry. A job that returned from `runWorker()` (done, blocked, or failed by the stall rule) is put on the `WorkerShelf` with its history; no `keep` is needed (`keep` is accepted, ignored and answered with a note by `grant.ts:planDispatch()`; the old `persistence`/`instance` names stay aliases in `AutomaTool.ts:normalizeAutomaInput()`). A worker belongs to its principal and its task alone and keeps its grant, model and system prompt. A history at `workers.ts:AUTOMA_RETAINED_INPUT_LIMIT` is parked to `<session dir>/subagents/automa/<activityId>/<id>.json` (atomic) when the worker goes idle, and any idle worker after `AUTOMA_IDLE_PARK_MS`; `continue` revives it from the file, also after a restart while the task is open. Workers end when the dispatcher's activity settles (`index.ts:Tools.sweepWorkers()`, run on store changes and an unref'd timer; the files are deleted), on `release`, or when the actor starts another task (`WorkerShelf.closeStale()`). `continue` on a closed, unknown or foreign id refuses the whole call with `Worker <id> is closed or unknown; dispatch a new job.`; a continue that throws leaves the worker as it was. Enforced by `tests/automa-workers.test.ts`, `tests/automa-tool.test.ts`.
- **A worker may carry an optional name, and a name is another way to write its id, never a second identity**: a job's `name` (`orchestration/AutomaTool/names.ts:nameProblem()`: lowercase kebab-case `^[a-z][a-z0-9-]*$`, at most `NAME_MAX` = 24, never shaped like an id) is validated by `grant.ts:planDispatch()` with a refusal and its fix, must be unique within the call and among the dispatcher's workers of the task (`workers.ts:WorkerShelf.names()` reads memory and parked files, `src/runtime/background-jobs.ts:BackgroundBoard.names()` the background jobs still running; a worker released by the same call frees its name) and is stored on `workers.ts:IdleWorker.name` and the parked file (old files without it load). `index.ts:Tools.runAutoma()` reads `continue`, `release` and `after` references as ids in any letter case, or as names (`graph.ts:resolveAfter()` also resolves a name of a job in the same call), and `BackgroundBoard.find()` does the same for `wait`; a continued worker keeps its name. The name is shown by `AutomaTool.ts:resultBlock()` (`name="scout"` after `id`), the swarm job state (`AutomaJobState.name`), `src/runtime/delegations.ts` (`workerName`), the team stream (`TeamItem.name`, `TeamEvent.workerName`, read by `src/runtime/team-stage.ts:workerName()`), the task graph node title and the headless delegations JSON; no name is ever generated. Enforced by `tests/automa-names.test.ts`.
- **Jobs follow jobs through `after`, and a job that waits holds nothing**: `orchestration/AutomaTool/graph.ts:resolveAfter()` resolves every `after` entry (an id the runtime will assign, `#n`, an exact title, or a finished worker of the same dispatcher and task) and refuses, whole and with the fix, an unknown reference, another dispatcher's worker, an ambiguous title and a cycle (named as `T1 → T2 → T1`); `grant.ts:planDispatch()` calls it with ids previewed by `workers.ts:WorkerShelf.reserve()` (`commit: false`, so a refused call burns none) and checks `writes` disjointness only between jobs `JobGraph.ordered()` does not join. `AutomaTool.ts:startAutomaDispatch()` starts a job when every job it follows ended `done`; a waiting job asks for neither a per-dispatch place nor a `max_running` slot. A prerequisite that ended `blocked`, `failed`, `cancelled` or `denied` ends every job after it, transitively, as `skipped` with stop reason `dependency_unmet` and `Not started: <id> ended <status>.` (never shelved, so it cannot be continued); a dependent's first message carries the prerequisites' result blocks (no `Trust:` line, no transcripts) after its brief, a followed shelved worker's block is kept on the shelf (`workers.ts:WorkerResult`). The staggered start of job 0 is off for an ordered dispatch. Enforced by `tests/automa-order.test.ts`.
- **A background dispatch returns a receipt at once and delivers results as messages, and its dispatcher's task stays open**: `mode: "background"` runs `AutomaTool.ts:startAutomaDispatch()` on a signal of its own (cancelled with the dispatcher's task, `index.ts:Tools.runAutoma()`, and by `src/kernel/agent.ts:createAgent()` whichever way the task ends). `src/runtime/background-jobs.ts:BackgroundBoard` (`Tools.background`) holds the jobs still open and the results not yet delivered; results ending within 3 seconds of the first one waiting go out as one message, a `blocked` result (with the jobs it skipped) and the last result of a dispatch go at once, through `AutomaEnvironment.deliver` (`src/app/request.ts` to `EnsembleRuntime.injectTaskMessage()`, queued: the path peer messages take) and are retried while nobody can receive them. `src/kernel/peer-wait.ts:PeerWait.pending` counts outstanding results, so the dispatcher's round does not close and an empty reply parks it with no model request (`PeerWait.park()`). `Automa({"wait": [...]})` claims the named jobs (`BackgroundBoard.claim()`), returns their blocks when they have ended and they are never sent as messages; unknown ids and ids of another task are refused. The swarm is published with `background: true` and each job's `delivered` flag even after the tool step ended (`src/runtime/steps.ts:Steps.swarm()`). Enforced by `tests/automa-order.test.ts`, `tests/automa-background-app.test.ts`, `tests/automa-order-views.test.ts`.
- **One dispatch at a time per actor, width and running count come from `[automa]`**: a call carries at most `max_per_dispatch` jobs (default 16, schema 32; more is refused with the fix by `grant.ts:planDispatch()`), `parallel` or `max_parallel` or the style's `parallel` is how many run at once within it, and `max_running` (default 24) is one `src/kernel/semaphore.ts:Semaphore` per session across all dispatchers, held only while a job runs; jobs beyond it show as `queued`. A dispatch of more than three jobs with one system prompt starts job 0 alone and the rest after its first model response (prefix cache). Read-only calls of one worker turn run in parallel groups of `permissions.readonly_concurrency` (`src/kernel/worker-run.ts:runWorker()`, `readOnly`; `src/kernel/tool-batch.ts` is bound to `AgentRun` and steps, so the worker repeats its grouping rule). Request-level limits belong to `src/providers/request-gate.ts`. Enforced by `tests/automa-workers.test.ts`.
- **The user's `/model automa` choice outranks every style and role model**: `orchestration/AutomaTool/preset.ts:chooseAutomaModel()`. Worker styles (`preset.ts:automaStyleSchema`) set only prompt flavour, model and concurrency; the runtime picks `default_style` (or `write_style` for jobs with `writes`) and a model may name one, but a style grants nothing. Enforced by `tests/automa-tool.test.ts`.
- **Automa routes by the grant, never by guessed difficulty, and has one automatic switch for images**: a job without `writes` runs on the read model (`tool-models.ts:AUTOMA_READ_KEY`, `automa-read`), a job with `writes` on the code model (`tool-models.ts:AUTOMA_MODEL_KEY`, `automa`); `src/app/request.ts` (`resolveModel(preferred, vision, writes)`) takes the bound model, else a style or role `model` that resolves, else `preset.ts:autoAutomaModel()` (read: cheapest T1, code: cheapest T2 of the session provider that is `src/providers/model-marks.ts:likelyToolCapable()`, by catalog price; a missing tier falls to the nearest lower, then the nearest higher one never above the session model's tier; nothing qualifying means the session model, never an error). The job schema has no `tier` field, so a dispatcher cannot pick a model per task, only mark `vision: true` (`AutomaTool.ts:automaJobSchema`) or give `writes`; the journal `end` event records `route` (`read`, `code`, `vision`). For a vision job `resolveModel` keeps the routed model when it can see images, else uses the `/model automa` vision fallback (`tool-models.ts:AUTOMA_VISION_KEY`, `automa-vision`); when neither can see, `AutomaTool.ts:executeAutomaDispatch()` refuses that job only (`Job "<title>" needs a model that can see images. Choose a vision fallback under /model automa.`) and the others run. A worker whose model cannot see images gets `providers/vision-fallback.ts` placeholders and `Images were omitted: <model> cannot see images.` under Not verified; the result block names the model as `model="<provider>/<model>"`. Enforced by `tests/automa-vision.test.ts`, `tests/model-marks-ui.test.tsx`.
- **A larger Director `Actor` dispatch is brief-checked first, and the check never blocks by failing**: for two or more new tasks, or one `prompt` over `brief-check.ts:BRIEF_CHECK_PROMPT_LIMIT`, and never for `resumeTask`, `src/actors/services.ts:ActorServices.execute()` calls the checker installed by `setBriefCheck()` (`src/app/request.ts` wires `index.ts:Tools.runBriefCheck()`) before any task starts. The checker is one Automa-style worker on the code model with the grant tools `Read`, `Glob`, `Grep` only (`grant.ts:JobGrant.tools`, so a `Write` call is refused by `index.ts:Tools.workerDenial()`), the system prompt `orchestration/ActorTool/prompt.ts:BRIEF_CHECK_SYSTEM_PROMPT` and usage charged to the dispatcher as `automa`. `blocked` starts nothing and returns the gaps as a non-error result; `briefCheck: "skip"` skips it; a failed check dispatches with `Brief check: failed (<reason>); dispatched without it.`. Enforced by `tests/actor-brief-check.test.ts`.
- **`Plan` is a service tool for the Director and companions, never for workers, and `node` links work to it**: `coordination/PlanTool/PlanTool.ts` runs through `ActorServices.execute()` (`serviceTools`), so no worker grant can include it; an `Actor` task or `Automa` job with `node` is refused whole with the fix when the active plan lacks that node (`prompts/runtime/plan.ts:planUnknownLinkNode`), otherwise the link `{activityId}` or `{automaJob: "<activityId>/<jobId>"}` is appended to the node (`TaskOrigin.planNode`, swarm job `node`), and a companion's assignment gains the `Plan context:` block after its brief. Enforced by `tests/plan-linking.test.ts`, `tests/plan-app.test.ts`.
- **A fork is an Automa job whose first request is its dispatcher's own request, byte for byte, and it never leaves that frame**: `fork: true` (actors only; refused inside a worker or fork and where no request is known, with the fix, `index.ts:Tools.runAutoma()`) makes `src/kernel/tool-batch.ts:runToolBatch()` hand the tool its `parentTurn` (the request exactly as the provider got it, the assistant message exactly as stored, the provider object that answered, the model key); it is never rebuilt. `fork.ts:forkBase()` turns it into the frame (the request without its messages and its diagnostic labels) and the prefix (the request's messages, the assistant message, a fixed `Forked. Your part follows.` result for the dispatching call and a fixed result for any sibling call); each fork then adds one user message (`orchestration/AutomaTool/prompt.ts:FORK_DIRECTIVE`, `Title:`, and the job text a worker gets). `runWorker({fork})` sends `{...frame, messages: [...prefix, ...projection of the fork's own messages]}`: the prefix is never projected again, so system, tool list (Finish and the refused tools are not removed), messages, model, thinking effort and cache key stay the dispatcher's and its prefix cache applies; the fork always runs on the dispatcher's provider (no read/code routing, `/model automa` does not apply, images follow the dispatcher's request). Refusals happen when a call runs, not in the list: `Tools.execute()` answers `orchestration/AutomaTool/prompt.ts:FORK_REFUSAL` for `FORK_REFUSED_TOOLS` and any orchestration-tier tool, and answers (never throws) a tool the fork cannot run. `Finish` is taken by name even when the list does not declare it; where it cannot be called, a plain text reply ends the fork with that text as the summary (`WorkerTerminal.undeclared`). Forks are job ids like workers (`kind: 'fork'` in the swarm state, `kind="fork"` and `cache="<n>%"` on the result block), can be continued from their own history behind the same prefix (the frame lives in memory in `workers.ts:IdleWorker.fork`; after a restart a fork cannot be continued), run at most `[automa] max_forks_running` (default 3, 1-8) per dispatcher (`index.ts:Tools.forkSlots`; the rest queue and the result says so), are charged to the dispatcher with category `fork`, and are never actors. A first response that read under 50% of its input from cache adds a note, and a provider that caches nothing adds one receipt line instead. Enforced by `tests/automa-fork.test.ts`, `tests/automa-fork-app.test.ts`.
