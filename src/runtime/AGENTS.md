# Module: Runtime, Kernel & Session Store (`src/runtime/`, `src/kernel/`, `src/store/`)

## 1. Scope
- **Owns**: Immutable `RuntimeStore` snapshots and their Zod contracts (`contracts.ts`), step clocks (`steps.ts`), input provenance and delivery schemas (`provenance.ts`, `delivery.ts`), host context messages (`context-updates.ts`), system event schemas (`system-events.ts`); the `src/kernel/` agent loop, execution recovery and scratchpad paths; the `src/store/` session persistence (journal, sessions, file locks, atomic replace). `kernel/` and `store/` have no signposts of their own and inherit this one.
- **Does not own**: Terminal rendering ([`src/tui/AGENTS.md`](../tui/AGENTS.md)); actor queues, delivery admission and dispatch ([`src/actors/AGENTS.md`](../actors/AGENTS.md)); context projection and compaction ([`src/context/AGENTS.md`](../context/AGENTS.md)); permission decisions ([`src/permissions/AGENTS.md`](../permissions/AGENTS.md)).
- **Design rationale**: [docs/modules/system-history.md](../../docs/modules/system-history.md) (system events, presentation, environment changes).

## 3. Common Changes
### Add a system event kind or presentation
1. Add the value to `system-events.ts:systemEventSchema` (`kind`) or `systemPresentationSchema`. `Message.systemEventKind` and `systemPresentation` in `contracts.ts` derive from these types.
2. Emit it through `src/store/system-history.ts:SystemHistory.emit()` (its `kind` parameter is typed from the schema), usually via `notice()` or `receipt()` in `src/application.ts`.
3. A new presentation needs a consumer: `src/tui/app.tsx` handles `status` and `welcome`; `isTimelineMessage()` and `src/tui/timeline/stage.ts` decide timeline visibility. Absent metadata must keep legacy rendering.
- Tests: `tests/system-history-presentation.test.ts`, `tests/system-history.test.ts`.

### Add a host context message kind
1. Add the kind to `context-updates.ts:runtimeContextMessageSchema`; add a `superRefine` check if it carries required `data`.
2. Create it only with `createRuntimeContextMessage()` and append it through `src/kernel/request.ts:contextAppender()`. Non-environment kinds must carry `data.activityId` (and a `slot`) to survive restore.
3. Decide whether the kind is request-only (`context-updates.ts:isTransientContext()`) and its restore behavior in `src/context/continuity.ts` (kinds other than `environment-*` and `capability-change` are kept only for the current activity, keyed by `slot`), then check budget in `src/context/budget.ts` and the encoders in `src/providers/http.ts` and `src/providers/disclosure/`.
- Tests: `tests/runtime-context-updates.test.ts`, `tests/tool-disclosure-context.test.ts`.

### Add a delivery kind
1. Add the value to `delivery.ts:deliveryKindSchema` and an entry to `deliveryPriority` (a `Record<DeliveryKind, number>`, so typecheck fails until you do).
2. Route it in `src/actors/delivery-queue.ts:DeliveryQueue` (only `human_steer` is grouped alone; all other kinds are coordination).
3. Producers: `src/actors/ensemble.ts` and `src/actors/services.ts`; persistence is automatic through `Journal.saveDeliveries()` (parsed with `deliverySchema`).
- Tests: `tests/message-delivery.test.ts`, `tests/human-input-delivery.test.ts`.

## 4. Hard Boundaries
- **Host context is typed, hidden and never authorization**: `role: 'context'` messages are persisted before request preparation and rendered as application context, never as a human request. Enforced by `tests/runtime-context-updates.test.ts`.
- **What a reply is and what it changes are separate**: `src/kernel/turn-outcome.ts:classifyTurn()` is pure and tests the situations in priority order (earlier kinds win); `src/kernel/reply.ts:settleReply()` performs the effects; the loop flags (closing follow-up, final text, recovery note, reminder counts) change only through the named transitions of `src/kernel/round-state.ts:RoundState`. The three "something new arrived" transitions (`newInput`, `waitEnded`, `replyOwed`) reset different members; do not unify them without a decision. Enforced by `tests/turn-outcome.test.ts`, `tests/round-state.test.ts`.
- **Waiting is a contract, not an enforcement**: the `Actor` dispatch result tells the Director that reports wake it automatically and not to re-check (`tools/orchestration/ActorTool/prompt.ts:dispatchedResult`); the runtime never withdraws or counts repeated reads, so a Director that re-reads while companions run is simply executed. An empty reply while companions run ends the round instead of triggering `no_delivery` recovery. Enforced by `tests/tool-pacing.test.ts`.
- **`SendMessage` type `ask` keeps a task open, never blocks work**: the call returns at once. An actor closing its round is first told to answer what it owes (twice at most, `src/kernel/round-state.ts:ASK_CLOSE_REMINDERS`), then parks with no model requests (`src/kernel/peer-wait.ts:PeerWait`) until a `reply` or other message arrives. There is no time limit while the recipient runs. When the recipient's run ends, however it ended, the asker is told to stop waiting (`src/runtime/asks.ts:AskBoard`). Actors parked in a cycle are detected and one is released so it can answer. The Director asks but never parks. Enforced by `tests/send-message-ask.test.ts`.
- **A step never outlives its work**: a `SendMessage` ask finishes when delivered (`ask · awaiting reply`, `answered` or `no reply` is a card summary derived by `src/tools/coordination/SendMessageTool/pairing.ts:pairSendMessages`, not a running step); `RuntimeStore` closes every open step of an activity that reaches a terminal status (`contracts.ts:settleStep`); restore closes any step its ledger left open, as completed or failed when the tool record carries a result and cancelled otherwise, with no live clock. Enforced by `tests/send-message-step.test.ts`.
- **No request carries an ensemble snapshot**: `src/kernel/request.ts:prepareRequest()` adds no per-request snapshot message (transient or stored), so consecutive requests of a normal tool loop are pure appends on every provider. Coordination reaches the model as events and tools instead (see `src/actors/AGENTS.md`); the only ensemble text in the ledger is the one `task-state` record with slot `ensemble` that follows a fold or a restart, appended through `contextAppender` from `requestBase().contextUpdates`. The `snapshot` context kind and old `director-facts` / `ensemble` records stay valid in old ledgers, and `director-facts` slot messages are still filtered out of non-append-only requests. Enforced by `tests/director-facts.test.ts`.
- **A polling companion loses its tools, not its task**: past three repeats it parks until a teammate finishes or a message arrives. Enforced by `tests/send-message-ask.test.ts`.
- **An answered never-executed turn leaves the request**: an assistant turn with tool calls whose every result carries `unexecuted` (set by `src/kernel/tool-batch.ts:runToolBatch()` for schema failure, a voided batch, truncated arguments, an unknown tool and the `TOOLS_RESTRICTED_RESULT` refusal; never for a permission denial, a tool that ran and failed, or an interruption) is dropped with its results by `messages.ts:withoutAnsweredUnexecuted()` once a later turn ran a call or delivered a final answer; until then repeated failures stay visible, and a turn that also carried user-facing text is kept. Projection only (ledger untouched, no assistant message rewritten), skipped on `appendOnlyHistory`; provider encoders pick explicit fields so `unexecuted` is never sent. Enforced by `tests/unexecuted-turns.test.ts`.
- **One Automa reminder per run**: six consecutive read-only results produce a single note when `Automa` is offered, never while the Director is waiting. It is a `reminder` context message appended after the tool results (slot `automa`), never a suffix on a tool result. Enforced by `tests/tool-pacing.test.ts`, `tests/transient-notes.test.ts`.
- **Repetition is told as a fact in the result, or once as a reminder**: `src/kernel/repeat-guard.ts:RepeatGuard` is observed in model order by `src/kernel/tool-batch.ts:runToolBatch()`. A text `Read` whose output equals the previous read of the same path, offset and limit in this activity, with no Edit or Write of that file in between (64 selectors remembered), gets `src/tools/ReadTool/prompt.ts:READ_UNCHANGED_NOTE` appended to its result. The same canonical call with identical arguments and an unchanged result three times in a row (`LOOP_STREAK`) adds one `reminder` (slot `loop`, `prompts/runtime/recovery.ts:repeatedCallNote()`) per streak, except for `LOOP_EXEMPT_TOOLS` (`ShellJob`, `ReadActor`, `ListActors`, `SendMessage`, `AskUserQuestion`, `LoadTools`, `_FinishRound`) and MCP calls, and never while the Director waits. It is independent of the Automa streak note (`src/kernel/tool-pacing.ts:ToolPacing`). Enforced by `tests/tool-repeat-guard.test.ts`.
- **Offloaded output is an index**: `src/kernel/scratchpad.ts:persistedIndex()` replaces a result over 32 KB with the tool name and an argument summary, size and line count, the saved file, how to read it, and the head (about 1.5 KB) and tail (about 0.5 KB) cut at line boundaries; callers pass the tool and arguments (`settleToolResults()`, `maybePersistLargeOutput()`'s `source`), and an existing index is never persisted again. Enforced by `tests/tool-output-index.test.ts`.
- **A `reminder` is a correction or nudge about the model's last step; facts are never reminders**: a hidden `reminder` context message (ask-owed and empty-reply nudges, execution recovery, the Automa suggestion) is stored for audit, sent at the tail of the request, and no longer sent once the model has answered. Tool results, reports, interruption markers and environment changes are facts and use their own kinds. The kind was called `recovery` before; old ledgers still hold it, `context-updates.ts:runtimeContextMessageSchema` accepts it and `isTransientContext()` treats it as a reminder, and it is never written or rewritten. It stays in the ledger for audit and restore but is projected only until an assistant message follows it (`context-updates.ts:withoutAnsweredTransient()`, applied beside the `finalizer` filter in `src/kernel/request.ts:prepareRequest()`). The projection is pure and order-only, so requests after the drop are byte-stable; a repeated identical note is appended again once the earlier one was answered. `src/context/continuity.ts:retainRuntimeContext()` never keeps them across compaction. The exception is the Anthropic protocol (`appendOnlyHistory`), where deleting a message is a history edit, so they stay in history there. Enforced by `tests/transient-notes.test.ts`.
- **A tool call that came out as text is not a delivery**: an assistant turn with no structured tool calls whose text contains `call:<namespace>:<Name>{` for a tool offered in that request (`src/kernel/text-tool-call.ts:textToolCallName`) executed nothing. It is recorded with `textToolCall: true` (raw text kept in the ledger for audit and in history so the model can reissue the call), shown on the card as the short `TEXT_TOOL_CALL_NOTE`, excluded from the final text, report and delivery (`store/journal.ts:Journal.finishRecord`, `actors/ensemble.ts`, `context/contracts.ts:summarizeRound`), and sent to output recovery as `text_tool_call` (`prompts/runtime/recovery.ts:executionRecoveryInstruction`, request-only, shares the truncation budget). Names not offered never match. Enforced by `tests/text-tool-call.test.ts`, `tests/agent.test.ts`.
- **The round title is the `_FinishRound` title**: `Journal.finishRecord` names a completed round after the accepted `_FinishRound` title; a stage line or whole-line parenthetical aside (`context/contracts.ts:isActionLine`) never becomes a title and falls back to the text-derived one. Enforced by `tests/round-memory.test.ts`, `tests/context-titles.test.ts`.
- **A delivered answer is never failed for a missing `_FinishRound`**: plain text without the call sets the final text (persisted once) and the agent sends exactly one follow-up (`src/kernel/round-state.ts:RoundState.closing`) whose tool list and tool-discovery settings equal a normal request's, so the cache prefix is unchanged; it carries only the request-only note `FINISH_ROUND_FOLLOW_UP`. Whatever that reply holds besides a usable call (business tools, unusable arguments, text, nothing), the runtime writes the `[runtime]` record and the round completes; business calls in it get an error result and are not executed. The follow-up is sent only where the activity closes a round (`runtime/round-scope.ts:roundEffect()`): a Director with dispatched work open, or a companion woken by a teammate, sends none and a `_FinishRound` call there gets an ordinary result and is ignored. Enforced by `tests/round-delivery.test.ts`, `tests/finish-round.test.ts`, `tests/round-boundaries.test.ts`.
- **Round closure through `_FinishRound`**: a successful receipt needs no further request; a call in the same batch as business tools executes nothing and is followed by the single follow-up above; arguments are accepted leniently (`context/round-memory.ts:normalizeFinishRound`: unknown fields ignored, legacy `outcome` / `verification` / `carry_forward` joined into `summary`, over-long values truncated by estimated tokens, a missing title filled from the stage line or task title); a round with no delivered text keeps the empty-reply recovery; cancellation and failure keep their real outcome. Enforced by `tests/finish-round.test.ts`.
- **Refused tools keep the tool list**: the exhausted-recovery turn (`AgentRequestBase.refuseTools` in `kernel/agent.ts`) never changes the request's tool list, because it opens the provider's cache prefix; calls get a `TOOLS_RESTRICTED_RESULT` error instead, and a second refused batch in a row fails the round without another request (`tests/tool-pacing.test.ts`).
- **Logox's user stop names its still-working companions**: `src/application.ts` `cancel()` passes their display names (from `runtime/round-scope.ts:roundScope`) as the stop detail of a Logox activity, and `actors/ensemble.ts:stopNotice()` turns them into `prompts/runtime/interruption.ts:userInterruptMarkerWithWorking`. Enforced by `tests/user-interrupt.test.ts`.
- **A deliberate stop is told to the model, once, by name**: when the stop reason is `user` (Esc) or `director_cancel` (CancelActor), cut-off tool results use `prompts/runtime/interruption.ts:USER_INTERRUPTED_TOOL_TEXT` / `DIRECTOR_INTERRUPTED_TOOL_TEXT` and the run's ledger gets one hidden `interruption` context message (`actors/ensemble.ts:stopNotice()`, appended before the round closes; never a timeline row); the round title becomes `Interrupted by user` / `Stopped by Director` (`context/contracts.ts:deliberateStopLabel()`). `shutdown` and restart recovery (`runtime/messages.ts` texts) keep the generic wording and add no marker. Enforced by `tests/user-interrupt.test.ts`.
- **Activity labels are optional and not status**: the only writer is the `⏵` status line (`src/kernel/reply.ts:presentTurn()`); the label is `{label, detail?}` (peers read it through `ListActors`) and `stageHistory` is no longer written; legacy milestone checkpoints, `UpdateTaskProgress` ledgers and `stageHistory` stay readable and are never rewritten. The card subtitle does not read it (see `src/tui/AGENTS.md`). Enforced by `tests/task-progress.test.ts`, `tests/progress-lifecycle.test.ts`, `tests/agent.test.ts`.
- **Status lines are not fed back**: `runtime/narration.ts:extractNarration()` takes a `⏵` only from the very start of the first line of the visible reply (never reasoning), stops at the line end or the first sentence end (the rest of the line stays in the reply), caps by display width (`NARRATION_MAX_WIDTH`, CJK and emoji two columns) and trims trailing punctuation; an empty result is no narration. The ledger text drops the line and the `stage` field keeps it (older ledgers carry it too), except a reply that is only that line (a closing `_FinishRound` does not count as work): its words stay as the reply text so the turn is never empty. Request assembly adds no stage lines to history (the old `withStageLines` is gone; sessions resumed from older ledgers change request bytes once). Enforced by `tests/narration.test.ts`, `tests/agent.test.ts`.
- **A busy target's Enter is held, not queued into the timeline**: a plain `queue` submit to a window whose task is `running` or `waiting_input` goes to `RuntimeStore.addPending()` (snapshot `pending`, never a message, activity or journal entry). `src/app/input.ts:settlePending` delivers the oldest one through `dispatchInput` once the owner has no live round and no queued human activity (so one round per held message, in order); `sendPendingNow()` steers it into the running round as `human_steer` (source `steered`, consumed by `drainInbox` at the next step boundary with `prompts/runtime/interruption.ts:USER_STEER_NOTICE` prefixed in the ledger and model message; falls back to a normal dispatch if the round just ended); `discardPending()` returns the text. `/` commands and idle targets dispatch immediately. Esc and tool processes are untouched. The list is saved to `pending.json` (`src/store/journal.ts:Journal.saveHeld()`) on every change, one write at a time, and reloaded on `--resume` with `restored: true`, together with human requests that were queued but never started. A restored message is never auto-sent: `settlePending` skips it, `Send` (`sendPendingNow`) steers it into a running round or dispatches it at once when its owner is idle, and `×` discards it (`src/tui/input/input-delivery.ts:pendingRowLayout()` shows `Restored · Send`). Enforced by `tests/human-input-delivery.test.ts`, `tests/input-queue-ui.test.tsx`, `tests/restart-queue.test.ts`.
- **Admission is durable before acknowledgment; history is appended only at consumption**: human steering keeps human provenance, actor packets stay data, stale targets are rejected, restart does not replay. Enforced by `tests/message-delivery.test.ts`, `tests/human-input-delivery.test.ts`.
- **System event metadata is optional and strict**: presentation is separate from kind and model input; only explicit non-timeline routes are hidden; restore marks replay without rewriting raw events. Enforced by `tests/system-history-presentation.test.ts`.
- **Raw journals are append-only and system events never enter model history**: Enforced by `tests/system-history.test.ts`.
- **Snapshots are deep-frozen; transitions produce new objects**: partially enforced by `tests/task-progress.test.ts` (legacy progress still parses); store-wide freezing is *Unenforced*.
- **Step clocks exclude queue and nested waiting time**: Enforced by `tests/runtime-steps.test.ts`.
- **The live Thinking clock is the current request only; streaming tool arguments show as `Writing <Tool>(<file>) · <n> chars`**: providers emit `Delta` kind `tool` (`messages.ts:Delta`, accumulated `chars`, `target` once parsed); `src/kernel/model-turn.ts` records it on the running step as `drafting` (`steps.ts:Steps.drafting()`, store writes throttled to 1 KB or 250 ms). When prose already closed the thinking step, a text-less, group-less `steps.ts:Steps.draftStep()` carries it and is dropped from the timeline once finished. Finished steps never keep `drafting`; the finished `Thought N times` total stays cumulative. Enforced by `tests/runtime-steps.test.ts`, `tests/provider-tool-drafting.test.ts`.
- **`max_iterations = 0` means no iteration cap**: the loop asks to continue only when `options.iterations > 0`. *Unenforced* (tests pass explicit caps).
- **Session tree layout** `state/sessions/<sessionId>/` with `director.jsonl`, `tasks.json`, `events.json`, `deliveries.json`, `pending.json` (held human messages), `README.md`, `subagents/<actor>.jsonl`: written by `Journal`. *Unenforced*; only the `events.json` mirror is asserted in `tests/system-history-presentation.test.ts`.

- **Outage wakes carry no failure card**: `outage.ts:isOutageWake()` marks a failed Director coordination wake whose recovery key is `provider:temporary:*`; the timeline (`src/tui/timeline/stage.ts`) and the `model_error` emitter in `src/application.ts` skip it because the actors backoff owns that wait (see [`src/actors/AGENTS.md`](../actors/AGENTS.md)). Enforced by `tests/provider-outage.test.ts`.

## 5. Dependencies
- **Director id**: `director-id.ts` (`DIRECTOR_ID`, `isDirector()`) is the single import-free leaf for the Director's actor id; any layer, including `src/prompts/`, may import it. Never write the literal `'logox'` for that meaning (`src/kernel/director.ts` re-exports it).
- **Depends on**: `src/tools/` (`_FinishRoundTool`, `src/tools/ui-format.ts` titles), `src/actors/` (`ActorContext` type), `src/context/` (round memory during `Journal.finish()`), `src/prompts/runtime/` (recovery and scratchpad text), `src/providers/` (`Provider` calls from the loop).
- **Used by**: `src/actors/` (activities, deliveries, journal checkpoints), `src/tui/` (snapshots and system messages), `src/application.ts` (store, journal, sessions), `src/context/` (journal ledger ranges), `src/permissions/` (scratchpad path check).
